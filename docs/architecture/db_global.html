Global DB — ~/.sim_bench/sim_bench.db

Shared SQLite database for cross-run state · Last updated: 2026-05-16

⚠️ Source of truth. Schemas defined across sim_bench/api/database/models.py (SQLAlchemy, 8 tables), face_cluster/run_history_db.py, and face_cluster/training_db.py (sqlite3, 3 tables). Any change to a table in this file requires updating this document in the same PR (CODE_REVIEW_CHECKLIST §7).
One file, two access paths. The same SQLite file is opened by two different drivers:
  • SQLAlchemy via sim_bench/api/database/session.py — 8 tables managed by ORM models with idempotent column migrations.
  • Raw sqlite3 via face_cluster/{run_history_db,training_db}.py — 3 tables managed by CREATE TABLE IF NOT EXISTS + idempotent ALTER TABLE migrations.
The two access paths do not share Base / metadata. They coexist because the face_cluster modules predate the API layer; merging them is a low-priority refactor.
Tables: API tables (SQLAlchemy): albums pipeline_runs pipeline_results people config_profiles universal_cache user_events face_overrides
face_cluster tables (raw sqlite3): action_log merge_training_data trained_models
PK primary key FK foreign key LIVE currently written LEGACY deprecated / read-only

Path resolution

All access goes through helper functions that resolve to the same path:

  • sim_bench/api/database/session.py::get_database_path() → ~/.sim_bench/sim_bench.db
  • face_cluster/run_history_db.py::get_db_path() → same path
  • face_cluster/training_db.py::get_db_path() → same path

The directory is created on first access. There is no schema-version handshake between the two access paths — they own disjoint table sets.

API tables — managed by SQLAlchemy (sim_bench/api/database/models.py)

Migrations are idempotent ALTER TABLEs in session.py::_migrate_new_columns. No version number — schema is "whatever the running code expects, with optional new columns added on init."

universal_cache SQLAlchemy · class UniversalCache

Cache for any feature computed from an image (embeddings, scores, etc.). Survives across runs and across pipelines.

ColumnTypeDescription
id PK autoIntegerSurrogate.
image_pathStringIndexed. Path to the source image (forward slashes).
feature_typeStringe.g. face_embedding, scene_embedding, iqa_score.
model_nameStringe.g. buffalo_l, dinov2_vitb14.
model_versionStringOptional version tag for cache invalidation.
data_blobLargeBinaryOpaque bytes (numpy serialization, JSON, etc.).
image_mtimeFloatSource-file mtime at cache-write time; used for invalidation.
created_at, last_accessedDateTime—

Unique constraint: (image_path, feature_type, model_name) — one cache entry per source-feature-model triple.

This is the table that makes re-running cheap. Re-running a pipeline on an unchanged album hits this cache for every cacheable step. Clearing it (sqlite3 ~/.sim_bench/sim_bench.db "DELETE FROM universal_cache WHERE feature_type='face_embedding'") forces re-embedding.

Overlap with pipeline_runs: the API's pipeline_runs table is for Albumify; action_log is for the FC App standalone path. They do not share rows. What's deliberately NOT in the global DB

  • Per-face data (bbox, embedding, blur, pose). Lives in the per-run DB.
  • Clustering structure (clusters, cluster_assignments, merge_decisions). Lives in the per-run DB.
  • Embeddings. Cached in universal_cache (global, key=image) and materialized into embeddings.npy per run.
  • Filter decisions (spec-032). Lives in the per-run DB.

This split is deliberate: per-run data is voluminous and ephemeral (each rerun produces fresh rows); global data is small and durable (identities, profiles, user corrections, cached features).
