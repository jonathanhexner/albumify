Per-Run DB Schemas — <run_dir>/_v4/face_clustering.db

Field-level reference for the relational store created on every face-clustering run · Last updated: 2026-05-16

⚠️ Source of truth. This document is the canonical field-by-field reference. The DDL lives in face_cluster/db/schema.py; the Pandera validators in face_cluster/db/validators.py. Any change to either must update this document in the same PR (CODE_REVIEW_CHECKLIST §7 / WORKFLOW.md gate).
One DB per run. Each run dir contains its own _v4/face_clustering.db. Both the FC App standalone path and the Albumify path produce this same layout (spec-030). Schema version is pinned at the application layer (SCHEMA_VERSION = 4); the SQLite user_version pragma carries the same value. Additive nullable columns do NOT bump the version per the locked decision in specs/033-data-integrity/MASTER_PLAN.md.
Implementation layer: raw sqlite3, no ORM.
  • Why no ORM: per-run DB is write-once-read-many. Each run produces a fresh DB; no in-run migrations needed. Bulk conn.executemany(tuples) outperforms ORM object construction.
  • Schema source of truth: face_cluster/db/schema.py holds CREATE TABLE strings (one per table). SCHEMA_DDL concatenates them for executescript().
  • Validation: not via SQLAlchemy. Two layers instead:
    • Object boundary — Pydantic (FaceRecord, MergeDecisionRow dataclass, etc.) at construction.
    • DataFrame boundary — Pandera (FACES_SCHEMA, FACE_SCORES_SCHEMA, FILTER_DECISIONS_SCHEMA in face_cluster/db/validators.py) just before INSERT.
  • Single writer class: face_cluster.run_exporter.RunExporter (spec-030 contract).
  • This is a deliberate choice — not legacy state. Spec-040 preserves it.
Scope of this document. Per-run DB only. For the global ~/.sim_bench/sim_bench.db (albums, pipeline_runs, people, universal_cache, action_log, training data, etc.) see db_global.html.
Tables: faces face_scores clusters cluster_assignments merge_decisions filter_decisions run_metadata
Target tables (spec-040 Phase 4): images scene_clusters scene_cluster_assignments scene_embeddings.npy
PK primary key BOTH populated on Albumify AND FC App runs ALBUMIFY ONLY populated on Albumify; NULL on FC App standalone (by design — FC App doesn't compute this signal) TARGET NOT populated today by either path; depends on follow-up work P-spec spec that lands the target state
Known schema gaps:
  • SIGHTING-064 — area is in mixed units (fraction² on Albumify, px² on FC App per SIGHTING-060). A canonical area_ratio column would resolve the unit confusion.
  • SIGHTING-065 — image-level fields (iqa_score, ava_score, sharpness_score, scene_cluster_id) are denormalized onto every face row instead of living in a dedicated images table.
  • SIGHTING-066 — scene side has no structured persistence at all: no images table, no scene_clusters table, no scene_cluster_assignments table, no scene_embeddings.npy. Scene embeddings exist only as opaque blobs in universal_cache; cluster assignments survive only as a denormalized id on faces. Images with zero detected faces have no row anywhere. Asymmetric vs. the faces side (faces / face_scores / embeddings.npy / clusters / cluster_assignments). All three gaps land together in spec-040 Phase 4.

facesDDL: face_cluster/db/schema.py::FACES_DDL · Pandera: db/validators.py::FACES_SCHEMA

One row per detected face in the run. 21 columns.

How to read this table. Three traceability columns per field:
  • Producer (Albumify) — the class / step / module that computes the value on the Albumify path. Bold = class name; italic = step name.
  • Producer (FC App) — same, for FC App standalone.
  • Writer to DB — the class method that puts the value into the SQLite row tuple just before INSERT. Always RunExporter._write_faces_and_scores for this table, but cited explicitly so the chain is unambiguous.

What this table makes visible.
  • One writer to DB for the entire faces table: RunExporter._write_faces_and_scores (good — single writer, spec-030 contract).
  • Two producer chains upstream: bridge-from-context-dict on Albumify, vs. face_cluster.embedding on FC App. 6 of 17 columns have different producers across the two pipelines.
  • Quality-gate fields (is_core, rejection_reason) are the exception — same class (QualityGater) on both pipelines, because both routes feed the same gater.
  • spec-040 collapses the two producer columns into one.
What this table makes visible. 6 of 17 columns have different origins on the two pipelines. 4 columns are sourced from a Pydantic/dataclass object (FaceRecord.attr) on FC App but from a context dict (PipelineContext.x[key]) on Albumify. This is the duplication that spec-040 (unification) collapses — see specs/040-unified-pipeline-framework/spec.md.

merge_decisionsDDL: MERGE_DECISIONS_DDL · dataclass: face_cluster/types.py::MergeDecisionRow

One row per (iteration, cluster_a, cluster_b) merge candidate evaluated by ConservativeMerger. 28 columns. Column order MUST match MergeDecisionRow.field_names() exactly — enforced by test_merge_decisions_column_order_matches_dataclass.

Producer for every column: ConservativeMerger._select_best_merge (in face_cluster.merge) — produces each row as a dict with the full 28-key set. Writer class: RunExporter._write_merges — binds positionally against MergeDecisionRow.field_names(), validated by _strict_validate_merge_log (rejects rows with missing / extra keys).

GroupColumnsDescription
Identity (5) iteration · cluster_a · cluster_b · cluster_a_size · cluster_b_size Which clusters this row is about, and how big each was at evaluation time.
Distance / threshold (7) exemplar_dist · threshold_used · T_a · T_b · T_global · p25_cross_dist · passes_cross Gate A inputs: per-pair exemplar distance, the threshold used to evaluate it (fixed or adaptive), and the cross-distance OR-gate evidence.
Support gate (3) support · unique_support · required_support Gate B: cross-cluster pair count vs required minimum.
Diameter gate (2) post_diameter · max_allowed_diameter Gate D: relative-expansion diameter check.
Margin gate (4) margin_gap · margin_dist_to_b · margin_competitor_dist · margin_competitor_id Gate C: gap between best and second-best candidate.
Per-gate verdicts (4) passes_exemplar · passes_support · passes_margin · passes_diameter Bool per gate (NOT NULL). 1 = passed.
Outcome (3) action · actually_merged · rejection_reason action ∈ {merged, passed, rejected}. actually_merged is true only for the iteration's executed winner.

Status: BOTH — fully populated since spec-030 (RunExporter migration) + spec-032 (filter_decisions companion). Field expansion (e.g., adding gate E for diameter-cap) would bump MergeDecisionRow + this table together (no nullable add).

filter_decisionsDDL: FILTER_DECISIONS_DDL · Pandera: FILTER_DECISIONS_SCHEMA · spec-032

scene_embeddings.npy + scene_embedding_image_paths.npy FUTURE · spec-040 Phase 4 · bulk numeric, not SQLite

Parallel to embeddings.npy on the faces side. Stored alongside face_clustering.db in the run dir.

Writer method: RunExporter._write_scene_embeddings_npy (new). Reads PipelineContext.scene_embeddings dict; serializes the matrix + the aligned image_path array.

  • scene_embeddings.npy — (n_images, embedding_dim) float32 matrix. Embedding model and dim depend on extract_scene_embedding.model (DINOv2 default = 768).
  • scene_embedding_image_paths.npy — (n_images,) array of strings aligning row order to image_path. Read together; reading one without the other is a contract violation (same rule as the faces side).

What stays unchanged on the faces side after Phase 4

faces drops 4 denormalized columns (iqa_score, ava_score, sharpness_score, scene_cluster_id — those move to images) and adds 5 (area_ratio, bbox_x_ratio, bbox_y_ratio, bbox_w_ratio, bbox_h_ratio; SIGHTING-064). The unit-mixed area / bbox_* columns stay deprecated for one release, then are removed.
