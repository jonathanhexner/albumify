sim-bench · Results page bug report

Why some Per-Image Metrics columns are blank

RESOLVED — spec-085 (2026-06-25) Fixed by making the break point (stage 5, ImageMetrics) the single source of truth: it now declares every field the producer emits, and _build_image_dict derives from it. A parity test prevents the contract from silently narrowing again. The walkthrough below is kept as the explanation of the original bug.
The symptom On the Results page, the "Per-Image Metrics" table shows the columns Body, Frontal, Central, Roll, BodyPose (and the newer Reason, Quality, Penalty) as empty — even though those numbers were computed and saved.
The cause, in one line The pipeline computes ~20 numbers per image and saves all 20. But the API's response "form" (a Pydantic class called ImageMetrics) has blanks for only 10 of them — and FastAPI silently throws away every field the form doesn't list. So the page never receives the other 10.

Plain analogy: ImageMetrics is an official form with only 10 blanks. Any number that doesn't have a matching blank gets dropped in the bin before the page ever sees it. No error is raised — the value just quietly becomes empty.

The smoking-gun proof

The table columns that work are exactly the fields ImageMetrics declares. The columns that are blank are exactly the ones it omits. That one-to-one match is how we know stage 5 is the gate — not stages 1–4 (data is fine there) and not stage 7 (it just draws what it's given).

Why this happened — and how to fix it

What went wrong

  • The same image record is hand-re-listed in several places (stages 2, 4, 5, 6).
  • ImageMetrics is narrower than the data behind it.
  • FastAPI drops undeclared fields with no warning — so the mismatch is invisible.
class ImageMetrics(BaseModel):
    path: str
    iqa_score: float
    # ...only 10 of ~20 fields
    # person_detected, filter_reason ... NOT here

The fix

  • Derive the API shape from one shared definition; don't re-list fields by hand.
  • Add a test asserting the response schema covers every produced field.
# one canonical schema + a parity test
def test_schema_covers_produced_fields():
    produced = set(build_image_metrics(sample))
    declared = set(ImageMetrics.model_fields)
    assert produced <= declared   # fails today

Senior engineer's take

This is a chain of data-transfer objects (DTOs — plain "carry the data" structs) with no single source of truth for the shape, plus two silent-failure layers: FastAPI's response_model drops undeclared fields, and the client dataclass defaults missing fields to None. Neither raises. Together they turn a simple schema mismatch into invisible data loss. Fix: make one schema canonical and add a parity test so the contract can never silently drift from the data again.
