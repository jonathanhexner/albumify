Albumify: what it takes to go public

Goal: a public website where a signed-in user uploads up to 1,000 trip photos and gets a curated album (best picks, why, people) that stays in their account. Order changed: ship first with the part that already works (the top 30), improve picking after launch. The current API is not exposed to the public: a new, small public API is built instead.

Two decisions behind this plan

1 · Ship first, tune picks later The top of the list is already good (owner kept 10/10 and 28/30); the long tail is weak. So the site shows the best 30 by default with "show more", and the quality work (Gate 1 verdict, near-duplicates, dull photos, sharpness) moves to after launch.
2 · New public API, not the current one Today's FastAPI grew around the owner's Streamlit app. Its problems:
  • many slow database round trips per page (Neon is 0.16 s away)
  • job state kept in server memory, lost on restart
  • endpoints shaped for Streamlit screens, ~60 of them, no auth or limits
  • queries scattered through services; worker code imports API code

Assumptions and risks

  • One developer + Claude Code. A second person on the website would save ~3-4 weeks.
  • Up to 1,000 photos (decided). ~25 min of GPU time plus a 20-40 min upload for 1,000 phone photos; the site warns first and lets the visitor come back by link. ≈ $0.40-0.50 per 1,000-photo run (estimate).
  • Showing only the top 30 hides the weak tail; the showcase trips must still be chosen so their top 30 look strong. Photos of people in them need consent.
  • Accounts are in v1 (owner decision 2026-11-22). Each album belongs to one user; face groups are personal data, so consent, delete-everything and a privacy policy are part of launch, not extras.
  • The old API is frozen, not deleted: the owner app keeps working; it gets no new features.
