SIGHTING-152 · measured 2026-11-13 · spec-117 R11

Why Albumify is slow on the cloud database

Albumify app pages served over Neon Postgres (cloud) vs the old local SQLite file. Same code, same Slovakia26 run (715 photos, 302 picks).

Answer
  • Pages are 5-15x slower on Neon and miss spec-117's target of 2 s per page (requirement R11). This blocks closing spec-117.
  • The database itself is not slow. The app asks it badly: list pages pull whole result records of up to 2.8 MB each to show a few counts, some pages ask once per row, and the Results page asks the same question up to 6 times per render. Locally each question costs microseconds, so nobody noticed. Over the network each costs 160-320 ms plus transfer.
  • Fixes are known and small: fetch only the needed columns, load related rows in one query, and stop the repeats. Estimate: half a day plus re-measurement. One extra cause is not Neon at all: first-time thumbnails are made from full-size photos.
  • After this fix, spec-117's remaining checks are one GPU session and the close-out. That session also supplies the missing evidence for specs 109 and 110, so up to five specs (109, 110, 112, 116, 117) can close in one merge.

4. Causes, largest first

C1 · Result list loads whole records to show counts

≈26 s
Where
sim_bench/api/services/result_service.py ResultService.list_results
What
For each completed run it touches run.result, which loads the full pipeline_results row (every photo's metrics and every step decision, up to 2.8 MB), and runs a separate count of people. It also returns step_decisions in the response, so the multi-MB JSON goes over HTTP too.
Evidence
10 queries and 4.1 s per call; 7 calls in the session. Same rows with summary columns only: 0.18 s instead of 2.0 s.
Fix
Select summary columns only, count people in one grouped query, drop step_decisions from the list response (the one page that needs it asks for that run).

C2 · Runs table asks for each run's album separately

≈20 s
Where
sim_bench/api/services/pipeline_service.py list_runs (Albums page)
What
Counts are already fetched column-only (an earlier fix). But run.album.name is loaded lazily, one query per run (26 per call), and every job is read from the jobs table. The first call also inspected the database schema (catalog queries).
Evidence
30-34 queries per call, 6.5-13.6 s per call; 26 of them are the same album lookup.
Fix
Load albums with the runs in one query (eager join), read only the job columns the table shows.

C3 · The Results page repeats the same calls

multiplies C1 + C4
Where
app/streamlit/pages/results.py: list_results is called in 6 places, picks/images in 4, all inside tabs that are built on every render
What
The UI keeps no copy of API answers between calls or reruns, so one Results render fetches the result list up to 6 times and the full result row several times.
Evidence
7 calls each of /results/ and /results/{id}/images in one visit sequence.
Fix
Fetch once per render and pass the data down; cache reads per run in the UI for a short time. A finished run's results never change.

C4 · Image list re-reads the full record

≈8 s
Where
ResultService.get_images (/results/{id}/images)
What
Each call reads the whole 2.8 MB row to return per-photo metrics. That data is needed, but not 7 times.
Fix
Solved by C3's caching; optionally read image_metrics only.

C5 · First-time thumbnails come from full-size photos

≈87 s oncenot Neon
Where
app/streamlit/components/gallery.py _load_thumbnail_cached
What
After a UI restart the gallery opens and shrinks 302 original photos (several MB each). The cache lives in the UI process and is lost on restart.
Evidence
Results 105 s on first open vs 18.4 s when opened again.
Fix
Use the 768 px display copies the pipeline already writes (local folder or R2). Needed anyway for a public site, where originals are not on the server.

C6 · Distance to the database

floor
What
Each round trip from this PC to Neon in us-east-1 costs 161-322 ms. The 2 s target therefore allows roughly 6 sequential queries per page after C1-C3.
Fix
Mostly removed by C1-C3. For the public site, the API will run next to the database (same cloud region), so the distance mainly affects this PC's test setup. A nearer Neon region is an option; it needs a decision.

7. Update: C1-C3 and C5 fixed, queries trimmed, reads in autocommit (same day)

Part 1: summary-only result list (step decisions moved to their own call), one joined query for the runs table, finished results kept in the API process, and the UI keeps result reads for 10 s. Part 2: thumbnails made from the run's 768 px copy (6 ms instead of 90 ms per photo; all five thumbnail loaders), the runs table in one query plus a 3-column jobs read, and the People list in one query without the 107 kB of face instances. Part 3: read requests (GET) run in autocommit on Postgres, with no BEGIN/ROLLBACK round trips; writes keep their transactions (checked live on Neon). Each step was re-measured with the same profiler and browser walk, after restarting both servers.

8. Method and limits

  • Profiling API: the real spec-117 API (branch spec/117-neon-r2 after merge b163e19) with a timing middleware and SQLAlchemy query hooks, on port 8012; UI on 8511 pointed at it. Database: Neon free plan, pooled endpoint, us-east-1.
  • Browser script: Playwright, 1500 px window, "page done" = Streamlit's running indicator gone.
  • API calls were logged per session, not per page, so the per-page split in section 3 is by subtraction, not measured per page.
  • Local comparison: the same pages on the spec-116 app over local SQLite (port 8501), one run.
  • Related, already fixed: SIGHTING-151 (Results gallery stopped at 231 of 302 picks: duplicate button keys); live app now shows all 302.
