Face Clustering Profile Parameters

Every knob in the Albumify "Configure & Run" page and the Face Clustering app, in plain language. For each: what it is, what raising vs lowering it does, its range, and its default. Pick a tab below.

Read this first. Every face is turned into a point in an abstract "embedding space." Two faces of the same person land close together; different people land far apart. We measure closeness with cosine distance: 0 = identical, 1 = unrelated. Almost every parameter below is a distance number on this 0–1 scale.

The question merge asks: after clustering, are two separate clusters actually the same person, split in two? Merge answers conservatively. Each cluster is a group of face-points with a few exemplars (representatives, the green-ringed points). Merge runs in rounds: each round picks at most one pair to merge, then starts over. It stops when no pair is convincing enough.

Step 1 — Propose candidates (decides nothing)

A cheap pre-filter just to narrow the field. A pair of clusters is even considered only if their closest exemplar-to-exemplar distance is ≤ merge_candidate_threshold (default 0.45, deliberately loose). This decides nothing — the four gates below do all the real work.

Step 2 — Four gates (a pair merges only if ALL FOUR pass)

Gate A — Agreement

The p25 (25th-percentile) of all exemplar-to-exemplar distances between the two clusters must be ≤ merge_exemplar_threshold (default 0.35). p25 means "a quarter of exemplar pairs are at least this close" — robust, so one lucky-close or one far-off pair can't swing the verdict.

OR-path for small clusters: with merge_use_cross_gate on (default), if the smaller cluster has ≤ merge_cross_max_size faces (default 5), Gate A can also pass when the p25 of all cross-cluster face-pair distances is ≤ merge_cross_threshold (default 0.40). Tiny clusters have too few exemplars for the exemplar test to be reliable, so this is a gentler alternative route.

Which path is stricter?

The exemplar test is the strict one; the cross test is the lenient fallback. Two reasons, same direction:

  • It's an OR, so cross can only loosen. Adding the cross path never blocks a merge — it can only let more through. So the exemplar test is the real bar; cross is an escape hatch.
  • Cross has the higher ceiling (0.40 vs 0.35) — easier to clear on its own.
  • Usually the raw number agrees too: cross looks at all faces (many pairs → p25 tends lower), while exemplars are deliberately spread apart (suppression radius), so their distances skew larger.

Big clusters: only the strict exemplar test applies. Small clusters (≤ 5): the lenient cross test can rescue a merge the exemplar test would reject — "be more forgiving when there aren't enough representatives to trust."

Gate B — Support

Not just one lucky close pair. Count the cross-cluster face pairs closer than merge_exemplar_threshold (the same 0.35). That count must be ≥ required, where required = max( floor(smaller_size × merge_support_frac), merge_support_min ) (defaults frac 0.3, min 2). With merge_support_unique on, each face is counted at most once (greedy 1-to-1 matching), so a single hub face can't fake broad support.

Gate C — Margin

The bridging exemplar must clearly prefer cluster B over the next-best competing cluster. For each exemplar, look at (distance to a competitor − distance to B); the worst_gap is the smallest such difference across all exemplars and competitors. Gate C passes if worst_gap ≥ merge_margin (default 0.05). This stops "tug-of-war" merges where a face sits halfway between two clusters.

Gate D — Diameter

Don't create a giant blurry cluster. The merged cluster's diameter (largest pairwise distance among its faces) must be ≤ (larger input cluster's diameter) × merge_diameter_expansion_factor (default 1.5).

Step 3 — Pick the winner, then repeat

Among all pairs that pass all four gates this round, merge the single one with the smallest exemplar p25 distance (the most-agreeing pair). Then re-run the whole round on the new layout. Stop when no pair passes all four gates.

Currently inactive parameters (read this). Five parameters below exist in the profile but have no effect today. The merge code uses the fixed merge_exemplar_threshold and never computes adaptive thresholds (verified in face_cluster/merge.py lines 288–290: "Fixed exemplar threshold (no adaptive computation)"; T_a, T_b, T_global are all None). They are documented for completeness but must not be read as if they work — this is tracked as a sighting: use_adaptive_merge_threshold, merge_exemplar_percentile, merge_global_percentile, merge_threshold_alpha, merge_threshold_beta.
