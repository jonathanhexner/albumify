TL;DR — your hypothesis was correct

The two apps store the same run differently. Albumify writes two copies of the merge log — one rich JSON file and one slimmed-down SQLite table. The standalone Face Clustering App writes only the rich JSON.

The reader (used by both apps) prefers SQLite when present. So a run created by Albumify hands the reader the slim copy. The slim copy is missing five fields. Those missing fields are exactly the values that look broken on screen ("191/0", "0.972/n/a", "4/4 REJECTED", "Actual merges: 0").

Algorithm is fine. Disk has the truth. Reader is reading the wrong copy.

Glossary — terms used in this document

merge log
One row per candidate cluster pair the merger evaluated, per iteration. ~17 numeric fields per row (gates, distances, sizes, thresholds, etc.). Source of truth for the Merge Analysis tab.
JSON file (merge_log.json)
Plain text file containing the merge log as-is. Whatever the merger produced is dumped to disk verbatim.
SQLite DB (face_clustering.db)
Embedded relational database with a merge_decisions table. Has a fixed column list; whatever isn't a column is dropped at write time.
"Lossy schema"
Plain English: the SQLite table has fewer columns than the JSON has fields. Writing into it silently drops the extras. Reading from it silently invents defaults (0, None) for the missing ones.
action vs. actually_merged
The merger evaluates many candidates per iteration. action ∈ {merged, passed, rejected} describes the gate verdict. actually_merged is a separate boolean — true only for the one winner per iteration that was executed.
Albumify / FC App
Two Streamlit apps. Albumify is the main album browser (port 8501). FC App is the standalone face clustering analyser (port 8502). Both share the face_cluster/ Python library.

The two apps and the shared library

Both apps go through the same face_cluster/ library. Bug isn't in either UI — it's in the library, but it only triggers for runs that have a face_clustering.db file on disk.

What "lossy schema" means, in plain terms

Why "actually_merged" missing is the worst of the five

~30 rows have action="merged" or "passed" but only 4 are real merges. The actually_merged boolean is what the UI uses to filter the 4 real ones from the 30 candidates. Strip that one column and the UI cannot tell winners from candidates → view.merges = [] and the iter-1 "passed" row for C0+C1 surfaces as a "REJECTED" candidate. SIGHTING-057 already hit this: the producer used to emit action="merged" for all winners-or-passes. Adding actually_merged was the fix. The DB schema then dropped that column on the way back.

Side-effect: "Margin: inf"

Config has merge_margin = 0.0 (gate disabled). The merger correctly returns worst_gap = float('inf'). The UI then prints the literal string "inf". Not a data bug — a missing display contract for "this gate is turned off."

Learnings — what to add to LEARNINGS.md

L1 · "App-asymmetric writes" is a real failure mode

Two apps that share an algorithm library can still disagree on what they persist. Audit any pipeline that has more than one entry point and compare the artifact set each one produces.

L2 · Lossy schemas are silent on the way in, lying on the way out

SQLite drops unknown fields without error. The loss only surfaces when the UI prints a default. Round-trip tests catch this; row-by-row writers do not.

L3 · "DB-first" is a default that ages badly

SQLite was added (spec 026) as a query convenience. Making it the primary read path turned a convenience into a single point of failure. JSON is the source of truth; the DB is a derived index.

L4 · Enum collapse always lies

The merger has three outcomes (merged / passed / rejected). The UI collapses them to two. Any boundary that loses enum values will eventually mislabel reality.
