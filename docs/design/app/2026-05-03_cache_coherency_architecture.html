Cache Coherency Architecture

How Albumify caches ML features, validates them, and what can go wrong

1. UniversalCache Table

SQLite database at ~/.sim_bench/sim_bench.db

Face-level features use a composite key. The mtime check extracts the real file path by splitting on :face_

3. What Gets Cached vs Recomputed

Cached (shared across runs)

  • Face detections (InsightFace SCRFD) — per image
  • Face embeddings (ArcFace 512-dim) — per face
  • IQA scores (MUSIQ) — per image
  • AVA scores (aesthetic) — per image
  • Scene embeddings (DINOv2) — per image

NOT cached (recomputed per run)

  • Quality filtering decisions
  • Scene clustering (HDBSCAN)
  • Face clustering (kNN + merge)
  • Selection decisions
  • People/person assignment

4. Cache Coherency Check Flow

This happens automatically during every pipeline run, inside cache_handler.py:load_from_cache()

1
Pipeline step starts (e.g., extract_face_embeddings). Generates list of CacheKey objects for all items to process.
↓
2
Calls cache_handler.load_from_cache(keys). Batches query in chunks of 200 (SQLite expression limit).
↓
3
For each cached entry found in UniversalCache table:
↓
3a
Extract source image path from composite key: "path/img.jpg:face_0".split(":face_")[0] → "path/img.jpg"
↓
3b
Get current file mtime: os.path.getmtime("path/img.jpg")
↓
3c
Compare: entry.image_mtime == current_mtime ?
Match → CACHE HIT
Return cached data_blob. Update last_accessed. Skip model inference for this item.
Mismatch → STALE
Delete entry from DB. Return nothing. Item will be recomputed by model inference.
File not found → INVALID
mtime returns -1. Delete entry. Source image was moved or deleted.
↓
4
Step processes uncached items only — runs model inference (expensive: 100ms-10s per item)
↓
5
Calls cache_handler.store_to_cache(key, data_bytes) for each newly computed result. Stores current file mtime.

5. Known Coherency Problems

SIGHTING-017: Two separate caches

Standalone face_cluster app uses file-based cache at {output_dir}/.embed_cache/. Main app uses UniversalCache (SQLite). No synchronization between them. Same image can have different embeddings in each cache.

SIGHTING-003/006: Face ID offset corruption

Historical bug: embeddings cached with wrong face indices (face 2 stored as face 0). Fixed, but no mechanism to detect if old corrupted entries still exist in cache.

Model version changes undetected

mtime check only validates source file hasn't changed. If model weights are updated (e.g., new ArcFace checkpoint), cached embeddings from the old model are still treated as valid. model_name is part of the key but model_version is not checked.

No blob integrity check

No checksum or hash stored alongside data_blob. A corrupted blob (disk error, interrupted write) would be returned as valid because mtime still matches.

7. Current Check vs Proper Coherency

What We Have (mtime only)

  • Check: file modification time matches cached mtime
  • Detects: file modified, file deleted, file moved
  • Misses: model version change, corrupted blobs, face detection changes (different # of faces found), embedding algorithm change
  • Speed: instant (single stat() call per entry)
  • Scope: per-entry during load, random sample in validator

Proper Coherency (re-extract + compare)

  • Check: re-run model on source image, compare output to cached embedding via cosine similarity
  • Detects: everything — model changes, corruption, face index shifts, extraction bugs
  • Cost: ~100ms-1s per entry (requires model load + inference)
  • Threshold: similarity > 0.99 = valid, < 0.99 = corrupted
  • When to run: after model updates, periodically on sample, when user suspects issues
  • Status: NOT IMPLEMENTED — requires loading InsightFace model in validation, which is slow and complex
