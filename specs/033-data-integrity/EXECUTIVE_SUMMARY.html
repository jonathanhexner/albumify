spec-033 · Data Integrity Cleanup

Executive summary for engineering leadership · 2026-05-15 · ~10-minute read

Bottom line. A single bridge file in our face-clustering pipeline was silently dropping five face fields and force-disabling five quality gates. That one boundary was the root cause of every symptom on SIGHTING-059 (cluster with no crops, blur=0 on 428 faces, NULL columns, empty filter audit table) and of the bigger user complaint: "FC App gives good results, Albumify gives worse results from the same data." We closed that bridge, plumbed the fields through, and installed runtime contracts at every boundary downstream so the failure mode can't quietly come back.

1 · The problem in one paragraph

Two Streamlit apps share the same face-clustering algorithm: the standalone Face Clustering App (FC App), used by analysts for tuning, and Albumify, the production photo-selection UI. They diverged in quality even though "they run the same code." Investigation traced the gap to sim_bench/pipeline/steps/face_cluster_bridge.py — the adapter Albumify uses to invoke the FC App clustering engine. The adapter did two destructive things:

  1. Converted FaceForClustering to FaceRecord and dropped five fields (blur_score, pose, det_score, landmarks, aligned_face) by either not reading them at all or using getattr(..., None) fallbacks.
  2. Hardcoded yaw_max=999.0, pitch_max=999.0, roll_max=999.0, blur_min=0.0, det_score_min=None — force-disabling the five quality gates that would have caught the consequences of step #1.

Every SIGHTING-059 symptom — cluster 6 with no crops, blur=0 for 428 faces, det/yaw/pitch/roll NULL in the DB, empty filter_decisions table, area unit drift (SIGHTING-060) — sits downstream of that one bridge. Beyond the immediate bug, the codebase had no contracts at the boundaries: typo'd config keys silently defaulted, UI sliders sometimes controlled nothing, and there was no single "show me everything about this image" reader for debugging.

2 · What we built (8 phases, one PR)

The plan was structured so every contract is enforced at runtime, not just documented. Pydantic protects object boundaries; Pandera protects DataFrame boundaries; architecture tests prevent re-drift. All eight phases shipped in a single session today.

3 · Where the contracts now live

This is the change-of-state worth remembering. Every arrow used to be a silent failure mode; every arrow now raises an error at the boundary the moment a contract breaks.

5 · What this means for the team

For analysts using FC App

The tooltips now tell you whether a knob actually does what the label says, and which step it writes to. Quality knobs that only work on FC App standalone (not on Albumify runs) are flagged explicitly so you don't save a profile with settings that get silently overridden.

For engineers adding a pipeline step

You can't ship a face-clustering step that takes a dict config — the architecture test rejects it. You write a Pydantic BaseModel, declare each field with Field(description=...), and the UI tooltip + the step's help text + the CI contract all point at the same source. You also can't add a field to PipelineContext without a row in spec-034; CI fails on drift in either direction.

For debugging a "why was this image rejected" question

One call: RunStore(run_dir).image_detail(path). Returns image scores, scene cluster, every face on the image, each face's cluster + exemplar status, every filter decision with measured values. No more cross-referencing JSON manifests against DB rows against context dicts.

For comparing FC App vs Albumify runs

python -m face_cluster.config_diff <run_a> <run_b> prints exactly the fields that differ. If the diff is empty and the outputs still differ, the divergence is in data, not config — which is itself a load-bearing diagnostic.

6 · Risks and what's not yet done honest

  • UI not visually smoke-tested. The Streamlit apps weren't started in this session — the user asked for an autonomous run-through. The new help= tooltips and the new "Min Face Bbox Ratio" slider should be eyeballed before merging.
  • Legacy v4 runs predate the new schema columns. Existing runs in ~/.sim_bench/ have NULL for iqa_score, ava_score, sharpness_score, scene_cluster_id. Pandera read-side validation may need a "warn vs. fail" mode for legacy runs — currently the schema is permissive on read.
  • Two pre-existing test failures left in place (test_faces_to_face_records_bridge references a classmethod that was refactored away; test_adaptive_threshold_fields_removed asserts fields were removed that weren't). Both unrelated to this PR.
  • Schema version not bumped. Per the locked decision in the master plan, the four new faces columns are additive with no version bump; a v5 cutover lands in a separate PR if desired.
  • Full pipeline migration to Pydantic configs is out of scope. Five face-clustering steps are typed; the other ~25 pipeline steps still take dict configs. A CI rule could be added later to require Pydantic for new face-clustering steps specifically.

7 · One thing to take away

The interesting engineering choice here wasn't the fix to the bridge — that was a 30-line change. It was deciding that "document the contract" wasn't enough: the same boundary had been documented and re-broken before. Pydantic + Pandera turn the contracts into runtime enforcement, so the next person who introduces a regression here gets a ValidationError at the boundary instead of a NULL column showing up in the UI three steps later. The architecture tests are the backstop, not the contract — the contract lives in the schemas.
