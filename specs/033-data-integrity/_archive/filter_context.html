What the inventory shows:
1. There are 22 real filters active today across image-, face-, and cluster-level.
2. Only 2 of them (filter_quality and the 4 merge gates) emit StepDecision with structured config + metrics. The other 8 either set a flag on the face dict (lost on export) or emit nothing.
3. Of 14 face-level filters, only 6 columns make it into faces.csv (the FC-App quality columns). The Albumify filters (filter_faces, insightface_*_score, filter_portraits) contribute zero columns to the per-face audit, despite being the filters that actually decided whether a face even reaches the FC App.

Part B.1 — Tracing "Min Face Size (px)"

The slider value is read in the Album App, wired into 4 step configs, and then quietly does almost nothing:

  1. Slider in UI
    app/streamlit/components/pipeline_runner.py:202-205
    st.slider("Min Face Size (px)", 20, 100, value=50, step=10, key="config_min_face_size")
  2. Wired to 4 step configs
    app/streamlit/components/pipeline_runner.py:307-312
    Same value goes into insightface_detect_faces.min_face_size, insightface_score_expression.min_face_size, insightface_score_eyes.min_face_size, insightface_score_pose.min_face_size.
  3. Consumer 1 — insightface_detect_faces
    sim_bench/pipeline/steps/insightface_detect_faces.py:128-129
    Stored in config_used for the StepDecision and nothing else. The step does not compare detected faces to min_face_size — every face InsightFace returns is kept regardless of size.
  4. Consumer 2 — insightface_score_expression
    sim_bench/pipeline/steps/insightface_score_expression.py:212-213
    if face_size < min_face_size or confidence < min_confidence: return 0.5 — small face still kept, but gets a neutral 0.5 score instead of being measured.
  5. Consumer 3/4 — insightface_score_eyes / pose
    sim_bench/pipeline/steps/insightface_score_*.py
    Same pattern: skip scoring on small faces, return default. Not a rejector.
Surprising fact: min_face_size is not a rejector anywhere. It only changes behavior in the 3 scoring steps, where it makes them return 0.5 instead of measuring. Detection itself ignores it. So changing the slider from 50 to 80 doesn't actually reject more faces — it just makes more faces get neutral expression/eyes/pose scores.

Part B.2 — The hidden min_face_ratio filter (3 copies, 3 defaults)

The real face-size rejector is min_face_ratio, which lives in three independent places:

  • filter_portraits.py:54-67 — Image-level: drops the whole image if NO face is >= min_face_ratio (default 0.02 = 2% of image area). Not exposed in UI.
  • filter_best_faces.py:56, 68 — Face-level: removes faces with face_ratio < min_face_ratio (default 0.02). Not exposed in UI.
  • detect_faces.py:183, configs/pipeline.yaml:70 — Image-level via crop_service.crop_faces(...). Config-file default is 0.005 (= 0.5%) — much looser than the schema default 0.02. Not exposed in UI.

None of these is exposed in the UI. The configured default in configs/pipeline.yaml is 0.005 for detect_faces (0.5% of image area), but the schema defaults in two of the steps say 0.02 (2%). Whichever default wins is determined by how the config dict is built up at runtime, which is not user-visible.

Why isn't it exposed?

Because no one ever moved it into the Configure & Run page. The plumbing exists — every step has a config_schema with a JSON-Schema entry for min_face_ratio — but the UI only renders sliders for the handful of params it explicitly enumerates. Adding it is mechanical (one slider in pipeline_runner.py), but it should probably be merged with min_face_size so the user picks a single unit on a single control.

Part B.3 — face.area unit drift across 3 producers

The same field name (face.area) carries different units depending on which producer populated it:

  • face_cluster/embedding.py:99 — FC App standalone run — area in raw pixels
    area = (x2 - x1) * (y2 - y1)   (bbox in absolute coords)
  • sim_bench/pipeline/steps/face_cluster_bridge.py:49 — Albumify export to FC App — area as fraction of image area
    area = float(bbox.get("w", 0) * bbox.get("h", 0))   (bbox.w / bbox.h are normalized 0..1)
  • sim_bench/pipeline/steps/filter_quality_gate.py:111 — Experimental FC pipeline — area in raw pixels
    area = w_px * h_px

The reference run (face_clustering_20260510_231628, mode main_app_export) goes through Albumify's bridge, so its face.area column is in fraction-of-image. The FC App's quality gate compares it directly against the slider value (default 0, label says "px"). The Face Analysis UI renders it as int(area) px², which is "0" for any fraction. Hence "Area 0 px²" on the reported face_26.

Part C — Proposed architecture

Current audit flow (what we have today)

Image-level filter (filter_quality) ─────┐ │ emits StepDecision per image ▼ context.step_decisions list │ pipeline_service persists ▼ pipeline_results DB table Face-level filter (filter_faces) ─────► face["filter_passed"] = False face["filter_reason"] = "..." (lives on the face dict, lost when Albumify exports to FC App) FC App quality gate ────────────────► faces.csv columns quality_*_pass / quality_*_value quality_rejection_reason (but only for the 4 standalone gates, not for the upstream Albumify ones) Crop stage ─────────────────────────► crop_path is either set or NaN NO reason column when NaN (this is the SIGHTING-059 #1 gap)

Proposed audit flow

┌───────────────────────────────────────┐ │ PipelineContext (existing) │ │ │ │ step_decisions : list[StepDecision] │◄────────────┐ └────────────┬──────────────────────────┘ │ │ │ every filter step (image OR face OR cluster) MUST emit │ one StepDecision per item it touches, with │ decision = "passed" | "rejected" | "skipped" | "merged" │ reason = human-readable │ config_used= the threshold actually used │ metrics = the measured values │ │ ┌─────────────────────────────────────────┐ │ │ export_for_analysis (PROPOSED) │ │ │ │ │ │ per-face step_decisions ──► faces.csv │ │ │ crop_skip_reason (new column) │ │ │ filter_steps (new JSON column) │ │ │ area_unit (new column: px or frac) │ │ │ │ │ │ per-image step_decisions ──► images.csv│───────────┘ └─────────────────────────────────────────┘
Concrete deltas:
  1. Every filter step in the inventory above gains one StepDecision append per item it inspects, with decision, reason, config_used, metrics populated. This is mechanical for the ones that already half-emit (filter_faces sets face["filter_passed"] but no StepDecision — just write the decision both places).
  2. The Albumify→FC export step (sim_bench/pipeline/steps/face_cluster_export.py and the bridge) inherits per-face decisions into faces.csv as new columns:
    • filter_steps_passed — comma-joined list of step names the face passed
    • filter_steps_failed — comma-joined list of step names the face failed (with the per-step reason)
    • crop_skip_reason — NaN on success, else an enum (landmarks_missing / alignment_failed / top_k_culled / write_failed) populated by the crop stage
    • area_unit — explicit unit declaration: "px" or "image_ratio"
  3. The FC App reads faces.csv via RunStore (already done in spec-030), and the Face Analysis tab renders area using area_unit instead of assuming px.
  4. Static-check test: test_every_filter_emits_step_decision grepping the steps directory for filter classes that don't append to context.step_decisions in their process().

How this closes the SIGHTING-059 issues

IssueHow the new architecture closes it
#1 cluster 6 has no crop The crop stage emits a StepDecision per face. If decision="skipped" with reason "landmarks_missing", that's persisted to crop_skip_reason in faces.csv. Querying "show me cluster 6" surfaces the reason inline instead of an empty thumbnail strip.
#2 face_26 area = 0 px² The export step writes area_unit="image_ratio" alongside the value, and the UI renderer dispatches on it. No more "0 px²" for a 0.001 fraction. The "Min Face Size (px)" slider becomes a real rejector after we either (a) make insightface_detect_faces enforce it, or (b) collapse it into min_face_ratio with explicit unit.
#3 max_diameter The proposed step is one more StepDecision producer — fits the same pattern. See feature request for spec.

Open question for you

Is the plumbing direction (every filter emits StepDecision, exporter propagates them to faces.csv) the architecture you want, or do you prefer something different (e.g. a separate filter_log.csv per run, or a row-per-(face,step) long table instead of wide columns on faces.csv)? Both fit the same need; the choice affects how the UI consumes them and how historical runs compare. I'd default to wide columns on faces.csv to match the existing pattern, but the long table is more queryable for "show me every face filter_faces rejected" questions.
