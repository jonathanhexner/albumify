5. Answer to your three direct questions

Q1. Can we reliably get this information from the DB?

Today: no, for runs that go through main_app_export. The schema is fine (faces, face_scores, cluster_assignments, filter_decisions all exist), but the writer drops fields (RC-2), writes wrong units (RC-1), and skips the filter_decisions table entirely (RC-4). For runs that go through the FC App's own pipeline, the data flow is already wired (spec-032 P0–P5) and the data is reliable — this is exactly why you observed the FC App running stand-alone "worked very well".

Q2. Can we add telemetry to the FC App?

Yes, and the table already exists — filter_decisions in _v4/face_clustering.db. We just need to (a) forward ctx.filters from the Albumify export shim and (b) bridge the three remaining Albumify filter steps so they record decisions. After that, every face gets a row per filter ("kept" or "rejected, reason=X, measured=Y") and a "Filter Decisions" tab in the FC App can read it directly via RunStore.filter_decisions().

Q3. What about the "Min Face Size (px)" slider we discussed?

It's currently a no-op (RC-5). The slider value flows into a comparator that's fed a fraction (0…1). Even at the most aggressive setting (e.g. ≥1000 px²), the comparison 0.5 >= 1000 is always false — but the comparator's direction is "reject if below threshold", and there's a short-circuit when the input doesn't look like pixels, so in practice nothing ever rejects. Fixing this requires RC-1 to land first (so the comparator is fed real pixel values).

7. Observability — make the next bug self-reporting

The reason these five bugs hid for so long is that no single screen shows what each filter did to each face. Two additions close that gap:

  • "Filter Decisions" tab in FC App. Reads filter_decisions via RunStore and renders a matrix: rows = images/faces, columns = filter names, cells = "kept" / "rejected: reason". One click drills to the face crop.
  • Image-level summary card on each image: "Detected 3 faces, kept 1, rejected 2: face_42 (low_quality), face_43 (top_k). Filter decisions: detector ✓, quality ✓, alignment ✗, top-k ✗ ✓ ✓." This is what you asked for as "complete observability for each image" — the data lives in filter_decisions with parent_id = image_path, so the query is a single join.

8. Self-test layer — fail loudly on regression

Three contract tests, each cheap, all CI-gated:

  1. Unit-check at write time. RunExporter._write_faces_and_scores asserts area is pixel-scale (heuristic: area > 1 OR (area == 0 AND bbox empty)). Catches fraction-vs-pixel drift the instant it's introduced by a new producer.
  2. Filter-coverage invariant. Architecture test: SELECT face_id FROM faces EXCEPT SELECT DISTINCT item_id FROM filter_decisions WHERE item_type='face' must return empty on every run produced after P-B. Fails if a future step bypasses FilterContext.
  3. End-to-end fixture test. Run the Albumify pipeline on a 5-image fixture, then assert:
    • every face row has non-NULL det_score, blur_score, yaw, pitch, roll
    • every cluster member has a crop file on disk
    • filter_decisions count == faces × (number of filters that run on each face)
    This is the test that would have caught the current state in CI before reaching you.
