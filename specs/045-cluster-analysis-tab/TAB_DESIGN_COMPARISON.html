History vs Cluster Analysis — Tab Design Comparison

Per-layer side-by-side: where the two tabs share design, where they diverge, and what the divergence tells us about the framework that's emerging from spec-042.

TL;DR

Same architectural skeleton; different bones inside. Both tabs follow the Tab → Service → Repository → DB layering established by spec-042 §B0. But two genuine design differences emerge:
  1. The Repository plays two different roles. History's Repository owns the schema for action_log. Cluster Analysis's Repository composes a pre-existing schema owner (RunStore). This produces two Repository flavors worth naming.
  2. Heavy compute introduces a new layer. Cluster Analysis's Service has to manage async compute (distance matrices take seconds). That introduces AsyncHandle[T] as shared library code — a new piece of the framework History didn't need.

The key conceptual difference

History's Repository is the source of truth for its schema.
Cluster Analysis's Repository is a typed query wrapper over a schema owned by RunStore.

This is the first time the codebase has both flavors visibly side-by-side. They're both legitimate. They obey the same external contract (B0 — typed Config, composable Criteria, typed errors). But they differ in how they relate to the schema beneath them.

Implications for the framework

  1. B0.1 (Column Registry) is conditional, not universal. The architecture standard should say "B0.1 applies to schema-owning Repositories" — query-shape Repositories opt out by construction. Worth a one-line clarification in architecture_standards.md.
  2. F-3 still hasn't fired. The "next Repository" turned out to be query-shape, so the extraction trigger is still pending. F-3 fires when the next schema-owning Repository appears (candidates: a future FaceLabelsRepository for v2 manual labels, or anything else that introduces a new SQLite table set).
  3. AsyncHandle is a new framework piece. Heavy-compute tabs need it; light-compute tabs don't. We're adding it in spec-045 because Cluster Analysis is the first heavy-compute tab. Future heavy-compute tabs (Face Analysis, Merged Clusters' diff view) reuse it for free.
  4. Snapshot-creating mutations are a third mutation flavor. History had in-place edits (update_comment) and pipeline-row inserts (start_action / complete_action). Cluster Analysis adds snapshot creation — a mutation that produces a new persistence root rather than modifying the existing one. This generalizes to: Recluster, Remerge, anything that "forks a run." Worth naming explicitly in architecture_standards.md §B3 (service vocabulary).
  5. The "Service builds a minimal PipelineResult to feed legacy compute classmethods" hack is the seam where the rebuild meets legacy code. Eventually ClusterView.compute / ClusterDebugView.compute should take typed inputs (ClusterResult + List[FaceRecord] + run config) directly. Filed as Open Question 5 in the spec; tracked as a follow-up.
Bottom line: spec-042's Tab → Service → Repository pattern generalizes cleanly. The new pieces (B0a/B0b distinction, AsyncHandle, snapshot mutations) are real and worth codifying — but they're refinements within the existing skeleton, not departures from it.
