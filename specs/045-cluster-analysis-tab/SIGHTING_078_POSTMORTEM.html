SIGHTING-078 postmortem

User-reported crash on the v2 Cluster Analysis tab, 2026-05-29. Root cause, class-level fault map, why it wasn't caught, what shipped, what's still pending.

Headline. The v2 Cluster Analysis tab crashed with RunStoreError: no clusters recorded for iteration 1 on a perfectly valid completed run. Root cause is a long-standing bug in RunStore's "final iteration" resolver — it queries the wrong table. spec-045 hits it because the new Repository delegates "final" resolution to RunStore. Workaround shipped in the Repository (resolves "final" locally now); root fix tracked as SIGHTING-078 against RunStore. Verified end-to-end against the user's actual run dir.

1. What the user saw — and the Streamlit fact behind it

RunStoreError: no clusters recorded for iteration 1 in
  C:\Users\Jonathan Hexner\.sim_bench\runs\52a70e6f068943798952e1a062705d75\face_clustering.db

File "...\main.py", line 53, in <module>
    render_cluster_analysis_tab()
File "...\tabs\cluster_analysis_tab.py", line 39, in render_cluster_analysis_tab
    service = _get_service(run_dir)
The non-obvious thing: you don't need to be on the Cluster Analysis tab for it to crash you. st.tabs([...]) in Streamlit is a layout container only. On every script rerun (any button click, input change, even a progress-bar update triggers one), every tab body executes top-to-bottom — visible or not. There's no lazy-render. So a crash inside render_cluster_analysis_tab() kills the whole page, even when the user is looking at the Run or History tab.

The actual sequence that fired this crash:

1. User clicks "Run pipeline" on the Run tab.
2. spec-050's run_tab writes v2_last_run_dir = <new UUID> IMMEDIATELY
   (deliberately — before the pipeline starts, for failure recovery).
3. Streamlit reruns main.py top-to-bottom (button-click trigger).
4. Line 50: render_run_tab() runs       (this is the tab the user can see)
5. Line 53: render_cluster_analysis_tab() runs  ← user is NOT on this tab
6. Tab's resolver reads v2_last_run_dir → loads the brand-new run dir →
   calls Service.compute_detail_async() (which the tab does eagerly when a
   cluster is selected from prior state) → Repository.get_cluster_result("final")
   → RunStore.clusters("final") → crashes on the no-op-merge shape.
7. Crash propagates up through Streamlit → entire page red traceback.

The 2-line traceback hid the deeper failure: the Repository constructed fine (the dir had a DB); the crash came later when the Service called RunStore.clusters("final") and got a RunStoreError. The earlier 2026-05-29 bug (empty UUID dir) had exactly the same shape — different error, same "tab you're not on tanks your page" mechanism.

2. The data shape that triggered it

Direct inspection of the user's run DB:

TableRows by iterationWhat it means
clustersiteration=0 → 15 rows15 clusters formed in the base clustering step.
cluster_assignmentsiteration=0 → 107 rows107 of 340 faces ended up in real clusters; 233 are noise (NOISE_LABEL).
merge_decisionsiteration=1 → 3 rows, all actually_merged=0The merger considered 3 candidate pairs and rejected all 3. This is normal and common on clean runs.
run_metadatan_iterations=1, n_clusters_final=15, status=completeRun reports complete. Clusters never changed past iteration 0.

So the schema convention is: the merger writes merge_decisions rows for every candidate considered, but only writes new clusters / cluster_assignments rows when something actually merges. When nothing merges, the "final cluster state" is just the previous iteration.

The bug lives in RunStore.iteration_count() — it reads merge_decisions instead of clusters. Two callers conflate "merger ran" with "merger produced clusters." spec-045's Repository inherits the bug by delegating "final" resolution to RunStore.

4. Why the test suite didn't catch it

Test layerCoverageWhy it missed
Repository synthetic (12) Construction, reads, criteria filters, mutation Synthetic fixture had 0 rows in merge_decisions. iteration_count() returned 0; "final" resolved to 0; matched the clusters table → no crash possible. The exact shape (merger ran, merged nothing) was never exercised.
Repository real (3) Construction + non-empty + metadata consistency Uses the most recent v2 Budapest run; happened to have merge_decisions rows that aligned with clusters rows (or had 0 rows). Coincidence.
Service synthetic (12) Async handles, force-merge gates, cancellation Same synthetic fixture as Repository tests. Same blind spot.
Service real (4) Compute completes against Budapest fixture Same coincidence as Repository real.
Architecture (5) Layering invariants (no DB in tab, typed returns, etc.) Architectural guard, not behavioral. Wouldn't catch this class of bug.
spec-060 E2E gate DRAFT — not implemented If shipped, it would run the v2 pipeline against a real album end-to-end + render every tab. The user's exact crash would have surfaced in the AppTest tab-render step before any commit landed.
The structural lesson. Synthetic fixtures that pass all the "easy" tests (correct iteration, no orphan rows, matching tables) are not sufficient. Real DBs have shapes you'd never write by hand — like "merger ran one round of pure considering." Until spec-060 ships, every Repository / Service test should explicitly construct one or two adversarial fixture variants ("what if column X is populated but column Y isn't?") or the spec-implementer agent should be required to run a real-data smoke before flipping any spec to Implemented.

5. What shipped

1. Repository workaround. ClusterAnalysisRepository.get_cluster_result("final") now resolves "final" locally via the Repository's own _resolve_iteration (which queries clusters directly, correctly) and passes the integer to RunStore.clusters(int). Bypasses RunStore's broken "final" resolver. 
def get_cluster_result(self, iteration: str = "final") -> ClusterResult:
    it = self._resolve_iteration(iteration)   # queries clusters table — correct
    return self._run_store.clusters(it)       # int path, not "final" alias
2. Regression test. test_get_cluster_result_final_when_merger_ran_but_merged_nothing in tests/face_clustering/repositories/test_cluster_analysis_repo_synthetic.py. Adds a merge_decisions row at iteration=1 with actually_merged=0 to the synthetic fixture, then asserts get_cluster_result("final") returns the iteration-0 ClusterResult instead of raising. This shape will now break CI if anyone regresses the workaround.
3. Logger fix. _get_service in the tab now calls logger.exception(...) on Repository construction failure. Future failures show up in logs/<ts>/fc_app_v2.log instead of vanishing into Streamlit's exception overlay. (Your "why am I not seeing it in my logger?" question — this closes the gap going forward.)
4. SIGHTING-078 filed against RunStore with full repro + workaround pointer + resolution options. The root fix belongs in RunStore (two candidate fixes documented), but isn't blocking and isn't in scope for spec-045.

7. Broader architectural exposure

One tab's bug = whole-app crash. Today main.py calls each tab's render function unguarded: 
with tab_run:
    render_run_tab()
with tab_analysis:
    render_cluster_analysis_tab()      ← unhandled exception here
with tab_history:
    render_history_tab()                ← never runs; user sees red traceback
A single exception anywhere in any tab body propagates up and kills the entire page render. The History tab and Run tab become inaccessible because of a bug in a tab the user isn't even looking at.

Recommended structural fix (separate from this sighting; worth its own micro-spec):

def _safe_render(tab_name: str, render_fn):
    try:
        render_fn()
    except Exception as exc:
        logger.exception("Tab '%s' crashed", tab_name)
        st.error(f"The **{tab_name}** tab hit an error: `{exc}`. "
                 "Other tabs still work; check the log for details.")

with tab_run:       _safe_render("Run",              render_run_tab)
with tab_analysis:  _safe_render("Cluster Analysis", render_cluster_analysis_tab)
with tab_history:   _safe_render("History",          render_history_tab)

~10 LOC + 1 helper. With this in place, today's bug would have shown a friendly red box inside the Cluster Analysis tab and left the Run/History tabs fully functional. The user would still have hit the bug, but only when they actually visited that tab.

Suggested action: file as a new micro-spec (e.g., specs/061-tab-isolation-defense/) or a sighting against app/face_clustering_v2/main.py. Not in scope for the current SIGHTING-078 fix — that one closes the specific RunStore mismatch; this one closes the wider "every tab is in the blast radius" exposure.

9. Honest answers to the questions you raised

QuestionAnswer
"I wasn't using the tab at all" — how is this related to cluster_analysis_tab? Streamlit's st.tabs is a layout container only — every tab's render function executes on every script rerun, regardless of which tab is visible. See §1's box. So render_cluster_analysis_tab() ran (and crashed) when you clicked Run, even though you were looking at the Run tab. That's a Streamlit fact that's easy to miss, and it's exactly why a tab-isolation wrapper (§7) is worth doing as a follow-up.
Did you actually run [the E2E test]? No. spec-060 (the E2E gate) is a draft only — zero phases implemented. The only thing the test suite ran was the synthetic regression test, which couldn't have caught this because the fixture didn't have the offending shape. After your bug report, I ran a one-off real-data verification (§6 above) — the fix works end-to-end on your actual run dir.
Why am I not seeing it in my logger? Two reasons. (1) The Repository's ValueError in the earlier 2026-05-29 bug was caught and re-displayed via st.error, not logged. (2) The RunStoreError in this bug propagated up through Streamlit's exception overlay (the red traceback box) before reaching any logger. Today's fix adds logger.exception(...) in _get_service so this whole class of failure hits logs/<ts>/fc_app_v2.log from now on. You'll need to restart Streamlit to pick it up.
