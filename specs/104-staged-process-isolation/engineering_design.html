Per-step process isolation for the pipeline

Bound the pipeline's peak memory to one model at a time instead of the sum of every model it loads — an executor-only change that leaves steps and pipeline construction untouched, gated behind a default-off flag.

1 · The problem (measured, not assumed)

The OOM is model-stacking — not image resolution.

Images are already downscaled to 768px; per-image working memory (crops, detections) is small (~67 MB for a whole trip). The cost is the models: the pipeline loads 5–7 separate neural nets, each a few hundred MB regardless of image size, and they never get freed.

Root fact: ONNX sessions drop on GC, but torch CPU memory is not returned to the OS on Windows even after del + gc.collect() — no empty_cache for CPU, no malloc_trim. Peak RSS = the sum of every model that ran (`faces` pipeline ~1.7 GB; full `default` 3 GB+) → OOM. Process death is the only reliable free().

2 · Approach — executor-only, steps unchanged

Run each step in a subprocess that exits.

The pipeline's steps already declare what they read and write (requires / produces) and the executor has a single run loop. That declaration is the marshaling spec, and the loop is the one place to wrap — so isolation is added entirely in the executor. No step changes, no change to how pipelines are constructed.

# PipelineExecutor._execute_step — one branch on a default-off flag
if config.isolate_steps:
    return self._execute_step_isolated(step, context, config)   # NEW path
# ...else the existing in-process path, byte-identical.

# the child (multiprocessing 'spawn'):
cls = import(step.__module__, step.__qualname__)   # rebuild the step by its own class
ctx = PipelineContext(**marshalled_state)          # rebuild context from parent
ctx.on_progress = lambda *a: queue.put(("progress", *a))   # relay progress back
step.process(ctx, cfg)                             # mutate context in place
queue.put(("ok", ctx.__dict__ - on_progress))      # ship mutated state back
# child EXITS → OS reclaims 100% of the model it loaded

3 · The boundary — what crosses, what doesn't

Serializing the context is a non-issue.

We audited every PipelineContext field. Everything that crosses is plain data; exactly one member isn't picklable, and it doesn't need to cross.

Crosses (picklable): score dicts, numpy arrays (embeddings, scene distance), FaceRecord dataclasses, sets, Paths, cluster dicts — the full requires/produces surface.
Stays in the parent: on_progress (a Callable, not picklable). The child relays progress messages over the queue; the parent fires the real callback. This is the only bespoke plumbing.
Never in the context: model handles live inside steps, not the shared context — so nothing heavy accidentally serializes.
v1 marshals the whole picklable context both ways for correctness (a step may touch undeclared keys). That's the source of v1's overhead — and the thing the deferred stage-grouping optimizes.

4 · Failure handling

A crashing step no longer kills the run.

Step raises → caught in the child, shipped back as an error → clean failed StepResult (same contract as in-process).
Child crash / OOM / segfault (no terminal message) → the parent detects the dead process, survives, and returns a failed StepResult with the exit code. Today an OOM kills the whole run with no traceback — this is a strict reliability upgrade.
Queue-drain ordering — the parent reads the (large) result off the queue before join(), avoiding the classic feeder-thread deadlock.

7 · Rollout & what's next

Ship dark, enable deliberately.

Now: merged behind isolate_steps=False — zero effect on existing runs. Enable per-run for memory-constrained / hosted paths.
v2 (optimization, not correctness): group contiguous steps into image / face / scene stages so big intermediates stay inside a child and spawn cost is paid once per stage. The spec already defines the groupings.
Then: this is the memory foundation the live curator (Albumify Direction B) sits on — a pipeline that provably fits in bounded RSS instead of one that OOMs.
