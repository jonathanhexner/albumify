PipelineGraph — API, parallelism, and the TDD path

Four questions answered: what the API is, whether graphs compose, how parallel jobs run without any cloud, and how we prove it works before building it out.

01 The API — pipeline vs graph, side by side

# TODAY — a pipeline mutates one shared context in-process
result: PipelineResult = execute_spec(spec, context)          # unchanged forever
        # spec    = PipelineSpec(steps=[...], step_configs={...})
        # context = mutated in place; results read off it afterwards

# NEW — a graph is a function: seed in, exports out. No shared mutation across nodes.
result: GraphResult = run_graph(graph, seed)
        # graph = GraphSpec(nodes={name: Node(...)})   loaded from pipeline.yaml
        # seed  = {"source_directory": ..., "image_paths": [...]}   plain dict

class Node:
    pipeline:  str            # a named pipeline in pipeline.yaml — the payload
    after:     list[str]      # dependency edges
    isolate:   bool = True    # False = run inline in the parent (cheap nodes)
    exports:   list[str]      # the ONLY context keys returned to the parent

class GraphResult:
    exports:      dict[str, Any]          # merged exports of all nodes
    node_results: dict[str, PipelineResult]  # per-node step timings/failures
    failed_node:  str | None
Pipeline (existing)Graph (new)
State modelone shared mutable context, steps free-for-allexplicit seed → exports per node; no hidden sharing between nodes
Unit of workstep (function)node = a whole pipeline (possibly in a child process)
Orderinglist + depends_on resolutionafter: edges; independent nodes run concurrently
Failure blast radiuswhole process (an OOM kills everything)one node; parent survives, reports, skips dependents
The graph never reaches inside a pipeline. It treats execute_spec as a black box — which is why the executor and all 30+ steps stay untouched.

02 Can a graph run a graph? Yes — same contract

Anything satisfying run(seed) → exports can be a node. A pipeline satisfies it; a graph satisfies it too. Composition falls out for free:

class Runnable(Protocol):                 # the one interface
    def run(self, seed: dict) -> dict: ...

PipelineNode.run(seed)  → exports        # wraps execute_spec in a child
PipelineGraph.run(seed) → exports        # a graph IS a Runnable → nestable

album_graph:
  people: {graph: face_processing_graph, after: [prep], exports: [people_clusters]}
          ↑ a sub-graph as a node — valid by construction
Policy: allowed by design, capped at depth 1 for now. Nested graphs mean children spawning children — legal on Windows, but process count and debugging complexity grow fast. The validator rejects depth > 1 until a real use case shows up. The point is the API doesn't have to change when one does.

03 Parallel execution — plain OS processes, zero cloud

"Send the job somewhere" = spawn a child process on the same machine with Python's built-in multiprocessing. No Azure/AWS, no Redis/Celery, no daemon, no new dependency — the stdlib and the OS scheduler are the infrastructure.

parent                                   what actually moves
──────                                   ───────────────────
ready = nodes whose after-deps are done
for node in ready:                        job = (node.steps, step_configs, seed)
    p = mp.Process(target=_run_node,  ──►      pickled over an OS pipe, ~few MB
                   args=(job, queue))
    p.start()                             child: imports sim_bench, opens cache DB,
                                                 runs executor, puts exports on queue,
queue.get() per finished node  ◄──────────       exits → OS reclaims ALL its memory
merge exports; mark node done; loop
ConcernAnswer
Why not a process pool?Pools reuse workers — a reused worker re-accumulates torch memory, recreating the bug. We need the exit. One fresh process per node.
Cost of a spawn~2–4 s (Python + torch imports) per node. 4–5 nodes ≈ 15 s overhead on runs measured in minutes. Cache DB is disk-backed → concurrent children don't fight (SQLite WAL, already how two apps share it).
How much parallelism?Only nodes with satisfied deps: in practice face ∥ scene (both model-light, clustering on embeddings). The heavy image node is serial by dependency. Cap = max_concurrent_nodes (default 2).
Another machine later?The job is already a picklable tuple; pointing it at SSH/a second box is a future transport swap, not a redesign. Explicitly out of scope now.

05 Scaling & cloud path — same graph, swappable transport

Two axes of parallelism. Spec-104 builds the first; the second is a future plug-in behind one seam. Cloud almost always means "many trips at once", not "one trip faster".

  WITHIN one trip — spec-104, one machine        ACROSS many trips — cloud, later
  image ─┬─► face  ─┐                            trip A ─► [worker] ─┐
         └─► scene ─┴─► select                   trip B ─► [worker] ─┼─► shared storage
  nodes · multiprocessing · bounds MEMORY       trip C ─► [worker] ─┘
                                                queue + N machines · bounds THROUGHPUT

The unit of cloud parallelism is one whole graph run (one trip) — each trip is independent. Inside a cloud worker the graph still uses local multiprocessing exactly as designed.

RungWhatCost postureWhen
0Bigger box — one rented VM (Hetzner/DO/spot), run the identical graphpennies/hr; kills the OOM outrightfirst real need
1Per-job container — one container runs one trip on demand (Modal, Fly Machines, Cloud Run Jobs)pay-per-second, no idle infrabursty / few users
2Queue + worker fleet — enqueue trips, N stateless workers pull & run, autoscale by depthlinear, controllablereal throughput
Avoid Kubernetes / EMR / Celery+RabbitMQ. Queue = a Postgres table or Upstash Redis. This is a batch CPU job, not a streaming platform.

Why the compute code doesn't change: a node is run(seed) → exports and a job is a picklable tuple. Local multiprocessing is just the same-machine transport; cloud is a different transport for the identical payload. We keep the seam clean now, build the remote runner later.

class NodeRunner(Protocol):
    def submit(self, job) -> Future[exports]: ...

LocalRunner  → mp.Process        # spec-104 builds this
RemoteRunner → enqueue + poll     # future plug-in — SAME job, SAME Node/exports contract
The honest catch — storage, not compute, is the real cloud cost. The graph is transport-ready; persistence is not. Multi-machine requires making these network-addressable — orthogonal to spec-104, its own future spec:
LayerTodayMulti-machine needs
universal_cachelocal SQLitePostgres or object store
image_cachelocal diskS3-compatible (R2 / B2 — cheap)

Cost kicker: isolation isn't only an OOM fix. Peak 1.2 GB instead of 3 GB per trip → ~2.5× more concurrent trips packed per worker → ~2.5× cheaper cloud bill. Spec-104 pays off in cloud economics even as a purely local change.
