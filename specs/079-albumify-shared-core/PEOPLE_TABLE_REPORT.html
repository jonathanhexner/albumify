spec-079 · People-Table History Report

The people table: what it is, what it was meant to be, and the gap

Commissioned to unblock spec-079 Stage 4 (slim people to authored-only). The destructive migration is gated on this report. Date 2026-06-05. Evidence is cited to file paths and line ranges; no code was changed.

One-line answer. The people table is not a narrow-by-design snapshot — it is the surviving data backbone of a much larger, deliberately-planned "Face Management" feature (2026-02-14) whose later phases (batch re-clustering, the full Needs-Help wizard, transparency/debug views, mobile) were never finished. The table itself is essentially complete; the feature it was built to serve is roughly half-built. There is no evidence of an even-broader vision (cross-album / persistent-named / re-identification) — that scope was never planned. So Stage 4's "slim to authored-only" is safe as a data-model change, but it should be made with eyes open that it sits under an unfinished UX, not a finished one.

1 · What the people table is today

A row in people is the API's denormalized snapshot of one face cluster, written into the central catalog DB (~/.sim_bench/sim_bench.db) after a pipeline run completes. The SQLAlchemy model is Person in sim_bench/api/database/models.py:83–116.

ColumnTypeMeaning
idString (UUID)Synthetic primary key. Not stable across runs — a fresh UUID every run.
album_id / run_idFKScopes the person to one album and one pipeline run. People are per-run, never global.
person_indexIntegerThe cluster id (0,1,2…) copied straight from people_clusters. This is the only link back to the clustering result.
nameString, nullableThe one piece of genuinely authored state. User-assigned name. Null until a human renames.
thumbnail_image_path / _face_index / _bboxString / Int / JSONThe chosen representative face for the card (best face or a saved crop path).
face_count / image_countIntegerCached statistics, recomputed on merge/split.
face_instancesJSON blobThe duplicated membership. A full copy of every face: {image_path, face_index, bbox, score, assignment_method, assignment_confidence}. This is what spec-079 calls "stale duplicate of cluster membership".
created_atDateTimeRow creation time.

Who writes it

PeopleService.create_from_clusters() — sim_bench/api/services/people_service.py:279–376. It is called once, from the pipeline completion path in sim_bench/api/services/pipeline_service.py:230–242, which prefers context.refined_people_clusters (from identity_refinement) over the raw context.people_clusters. For each cluster it flattens every Face into a JSON instance and snapshots it into the row. Mutations (rename / merge / split / delete_for_run) also live in this service.

Who reads it

  • BE routers/people.py (list / get / images / rename / merge / split) and the face_management read paths via face_service.py.
  • FE Albumify: pages/people.py, components/people_browser.py, pages/people_faces.py, and the People tab inside pages/face_management.py — all over HTTP via api_client.py.

How it relates to the run-directory clustering result

The run-dir DB (runs/<id>/face_clustering.db) that FC v2 reads has no person or name concept at all. It stores clusters and assignments only:

  • clusters (run_db/models/cluster.py): cluster_id, iteration, size, diameter, avg_intra_dist, origin, parent_ids.
  • cluster_assignments (run_db/models/cluster_assignment.py): face_id → cluster_id, iteration, is_exemplar, d10_score.

The defining equation

people = clusters + human edits. A cluster is an algorithmic fact in the run-dir DB. A Person is that cluster plus a name, a chosen thumbnail, and any merge/split the user performed — copied into the catalog DB. Everything in a Person row except name / thumbnail_* / user-driven merge-split is re-derivable from the run-dir DB.

2 · Original intention — was it meant to be more general?

I scanned every specs/*/spec.md, the specs/*/*.html plans, docs/PLAN_*.md, FEATURE_REQUESTS.md, LEARNINGS.md, and the archive. Two findings, in opposite directions.

Finding A — YES, it was the backbone of a much larger planned feature

The people table was the data layer of a fully-specced "Face Management" feature, written 2026-02-14, two documents totalling ~3,000 lines:

  • face_cluster/docs/archive/FACE_MANAGEMENT_UI_PLAN.md (1,037 lines) — goals, 7 phases, task breakdown, tests, a11y.
  • face_cluster/docs/archive/FACE_MANAGEMENT_MODULES.md (1,951 lines) — module-by-module specs for 14 components.

These docs explicitly treat Person as the pivot the whole feature hangs on. The diagram in UI_PLAN marks Person as "(exists)" and builds FaceOverride, FaceService, faces.py around it. The planned scope:

"Allow users to correct face clustering mistakes … Enable batch corrections with deferred reclustering … Support 'Needs Your Help' recommender for borderline cases." Success criteria include: assign / remove / reassign / create new person / untag / mark not-a-face / undo any action / answer Needs-Your-Help prompts / queue changes in batch mode. FACE_MANAGEMENT_UI_PLAN.md §1, lines 26–43
Batch apply was meant to: "Re-run identity_refinement step … Return updated face list + newly auto-assigned" — i.e. user corrections feed back into clustering and pull in more faces. FACE_MANAGEMENT_UI_PLAN.md §5.2 change-flow, lines 489–504

So the people table was never meant to be a passive read-only snapshot. It was meant to be a living, user-editable identity store with a rich correction UX and a feedback loop into the clustering algorithm. The 7 planned phases:

1 · Backend foundationFaceOverride model, faces.py, FaceService, schemasDONE

The single hardest piece of evidence that the feature was abandoned mid-way: the re-cluster feedback loop — the centrepiece of Phases 4–5 — is a stub that returns hardcoded zeros:

# TODO: Implement full reclustering
# For now, just return zeros
return {'auto_assigned': 0, 'still_unassigned': 0, …} sim_bench/api/services/face_service.py:742–757 (_trigger_recluster)

Finding B — NO broader "cross-album / persistent identity" vision was ever planned

I searched the entire repo for cross-album, persistent, across runs/albums, global identit*, known people, person gallery, re-identif*. Zero hits in any spec, plan, or feature request. The terminology spec (docs/design/app/2026-05-01_dataset_album_run_terminology_spec.md) and every Face-Management doc keep identity strictly per-(album, run). The Person model itself bakes this in: a UUID id minted per run and a hard run_id FK, with no natural identity key that could survive a re-run.

Note one easy false lead: the ML-merging plan (docs/PLAN_ML_CLUSTER_MERGING.md) and FC v2's detect_persons pipeline step both use the word "person", but neither is about the people table. detect_persons is person/object detection (bounding boxes), and the ML plan uses "person_A / person_B" only as training labels for a cluster-merge classifier — not a stored identity.

Direct answer to "was it meant to be more general?"

More general in function: yes — it was meant to be an editable identity store driving a full correction/recluster UX, not the read-mostly snapshot it is now. More general in scope (cross-album, persistent, ML-identity): no — that was never on any roadmap. The under-delivery is in the depth of the per-run feature, not in a missing breadth of vision.

FC v2 — does it have any people concept?

No. A search of app/face_clustering_v2/ and face_cluster/views/ finds zero "person/people/identity" matches in the views layer, and only 3 incidental hits in v2 (cluster_metrics.py, cluster_pair_crops.py, and the detect_persons step name in pipeline.py — all unrelated to identity). FC v2 deals exclusively in clusters; the "person" abstraction exists only on the Albumify/API side. This is precisely the divergence spec-079 exists to close.

5 · Assessment (blunt)

Today's people table is a finished data structure under a half-finished feature.

The table and its CRUD (create/rename/merge/split) work and are exercised by the People page. But the table was designed to be the spine of a rich "Face Management" correction system — and that system was abandoned around Phase 4 of 7. The most valuable planned behavior, the one that justified the whole denormalized face_instances design (user corrections feeding back into clustering to auto-pull more faces), is a stub returning zeros. The Needs-Help "wizard" degraded to a flat list of cards; the transparency views (distances, "why not assigned", exemplar galleries) and the entire mobile/a11y phase were never built.

What was dropped or deferred: (1) batch re-cluster feedback loop — never built; (2) the Tinder-style borderline wizard with keyboard/swipe — degraded to cards; (3) per-face distance/transparency & exemplar debug views — never built; (4) mobile detail sheet, gestures, a11y — never built. What was never even planned: any cross-album, persistent, or ML-assisted identity — so spec-079 should not feel it is abandoning a grand vision by slimming the table; it is only retiring a denormalized cache that an unfinished UX no longer fully uses. The genuinely authored state worth preserving is tiny: name, thumbnail_*, and the user's merge/split intent. Everything else in the row is re-derivable from the run-dir DB — exactly the premise of Stage 4.
