Are we done?  No — ~60% there

The execution layer is unified and shipped: both apps now submit a PipelineSpec to one validated primitive (execute_spec). What is not done is the goal that actually matters — identical config → identical clusters. On the binding benchmark the two apps still disagree (8 vs 20 identities), and we have now pinned the cause precisely. A partial fix is in the working tree (uncommitted) that closes most of the gap (20 → 13) but does not yet reach equivalence.

1. The objective, restated

One pipeline infrastructure for both products; one clean contract from each frontend into that pipeline; and the acceptance property that the same configuration run through either app produces the same result. We decomposed this into three layers. The headline finding of this review is that they are at three different maturities — and conflating them is what made it feel "almost done" when it was not.

LAYER 1 — EXECUTION how a pipeline runs DONE LAYER 2 — CONFIG how the frontend talks PARTIAL (FC v2 typed; Albumify untyped) LAYER 3 — STEP CHAIN what actually runs DIVERGENT <-- the behavioral gap lives here

2. Layer 1 — Execution Done

Both entrypoints now build a PipelineSpec (ordered steps + per-step params) and hand it to a single primitive. There is no second runner, no per-app hardcoded executor pass.

FC v2 UI / CLI Albumify API run_profile.py / run_pipeline() PipelineService.execute_pipeline() | | | PipelineSpec(steps, step_configs) | PipelineSpec(run.steps, run.step_configs) v v +--------------------> execute_spec(spec, context) <--------------------+ | validate_spec_or_raise() # mandatory steps, deps, typed params | PipelineExecutor.execute() # ONE pass over spec.steps | +--------------------+--------------------+ v v FC v2: RunExporter -> v5 run dir Albumify: PeopleService -> central DB (persistence is caller-owned by design)

SW-engineering note. The split is deliberate and correct: execution + validation are shared; persistence is not (FC v2 writes a v5 run dir, Albumify writes people rows). This is the right seam — forcing a shared persistence layer would have coupled two products that legitimately store different things. Verified by reading sim_bench/pipeline/run.py and sim_bench/api/services/pipeline_service.py:167.

So the two frontends do not yet speak the same language to the pipeline. Unifying on FCParams as the single contract is open work (Stage 4). Note: ClusterPeopleConfig does already expose the gate knobs (yaw_max, pitch_max, roll_max, blur_min, det_score_min) — so the divergence below is not a missing-knob problem. The knob was set; its input data never arrived. That distinction is the crux of this review.

The algorithmic finding: it is the POSE gate

We proved (Stage 0b, scripts/localize_gap.py) that the clustering code is equivalent — the bridge and the 8 unified steps agree sub-stage for sub-stage on identical input. The divergence is therefore entirely in the face set that reaches the identical clusterer:

FC v2 core set
133
Albumify core set
186
 +53 faces  =  the entire gap

Stage 0c (scripts/diff_face_sets.py) attributed those 53 extra faces exactly: they are off-angle faces that FC v2's pose gate rejects (pose_yaw 46 + pose_pitch 7, under profile_5's yaw≤30/pitch≤25). Albumify rejected zero of them — because on the Albumify path FaceRecord.pose was None for every face, and the gate is permissive when pose is absent. Same images, same faces, same gate config — the gate simply had no pose data to act on.

WHY pose was None on the Albumify path (the concrete bug) insightface_detect_faces -> serializes pose as a [yaw,pitch,roll] LIST under key 'pose', keyed by a canonical forward-slash path | face_cluster_bridge -> (a) looked up faces by the raw backslash Windows path -> MISS .faces_to_face_records() (b) read pose only from a dict under 'pose_scores' -> MISS | FaceRecord.pose = None for every face | pose gate passes 53 off-angle faces it should reject | core 133 -> 186 ===> 8 identities -> 20

This is a textbook "plumb the field through needs an upstream producer" failure (already in LEARNINGS, 2026-05-15): a gate was unlocked at the boundary while its input silently never arrived. Two independent defects compounded it — a path-key mismatch and a shape mismatch (list vs dict).

8. Recommendation

  • Do not commit the edited golden fixtures yet. They re-baseline the expected answer to 13, which would silently bless a non-equivalent state as correct. The anchor is 8.
  • Sequence: Stage 1 (RED test) → Stage 2 (blur) → Stage 3 (pose at producer) → re-baseline goldens once 8==8. The in-flight bridge patch is a useful diagnostic confirmation, but the durable fix belongs in insightface_detect_faces so both apps benefit and Stage 5 can delete the bridge cleanly.
  • Reframe "done." Execution unification shipped; that is real progress. But the product-visible goal — same config, same people — is gated on Stages 2–3 and is currently verified absent (8 vs 20). We should report it that way.
