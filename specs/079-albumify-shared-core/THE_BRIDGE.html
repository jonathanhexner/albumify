The "bridge" and the "buggy converter" — and the proposal

Why Albumify (13 identities) still differs from FC v2 (8), in precise terms. spec-079 · 2026-06-08

In one line. One detection step produces the face data in two forms: a clean typed list (face_records) and a raw dict (insightface_faces). FC v2 uses the clean list. Albumify throws it away and rebuilds the typed faces from the raw dict through a deprecated module — the bridge — whose rebuild step (the buggy converter) loses or corrupts face attributes. That rebuild is the source of the remaining divergence. The proposal: delete the rebuild; have Albumify use the clean list FC v2 already uses.

1 · The starting point — one step, two forms of the same data

3 · What "the bridge" is

sim_bench/pipeline/steps/face_cluster_bridge.py — a module whose own header says "DEPRECATED — scheduled for deletion in spec-040 Phase 7… Do not add new callers." It exists only because Albumify's cluster_people step still calls it. It does three things:
  • faces_to_face_records() — the "buggy converter." Takes the lightweight FaceForClustering objects and rebuilds full FaceRecords, re-looking-up the missing attributes (pose, blur, det, landmarks) from the raw insightface_faces dict.
  • build_fc_config() — turns the step's config dict into the algorithm config.
  • run_face_cluster_knn() — runs the clustering.

Why it's whack-a-mole: the bridge is a second, parallel re-implementation of building face data. Every attribute it has to re-derive is a chance to drift from FC v2. Fixing them one at a time never ends — the next attribute is always waiting.

5 · The proposal

Delete the rebuild. Have Albumify use context.face_records — the clean typed list FC v2 already uses — and run the same unified clustering steps on it. The clean list is already produced by insightface_detect_faces on the Albumify path; cluster_people simply ignores it today.

What this removes, by construction

  • pose / blur / fingerprint divergences — gone, because Albumify stops re-deriving faces and uses the same objects FC v2 does.
  • the build_fc_config blur pin — gone, because the unified quality_gate step honors the real blur_min and computes blur itself.
  • the deprecated bridge — no longer called (finishes spec-040 Phase 7).

What it does NOT change

  • Albumify keeps its own extra steps (scene clustering, selection) and its own persistence (the people table). Only the face-identity clustering portion switches to the shared clean path.

Honest caveat

Albumify's producer chain still runs a couple of steps FC v2 doesn't (e.g. filter_faces), which can drop ~3 faces. After the switch I will measure, not assume: if a small residual remains, it is that producer-step difference — a separate, visible question — not the bridge. I won't call it "aligned" until one run shows Albumify == FC v2 == 8.
