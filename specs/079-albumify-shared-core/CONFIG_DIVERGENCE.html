Why Albumify and FC v2 cluster differently

Same pipeline architecture, three config vocabularies, one deprecated bridge. spec-079 Stage 0 diagnosis · ref album Budapest2025_Google_14 · 2026-06-06

TL;DR. Both apps run the same clustering steps, but they build the algorithm config (FCConfig) two different ways. FC v2 uses a contract-enforced 1:1 copy (FCParams.to_fc_config()). Albumify routes through a hand-rolled, deprecated bridge (face_cluster_bridge.build_fc_config()) that (a) reads a different, smaller set of key names, (b) defaults merge/split/attach OFF, and (c) pins blur_min=0.0. On top of that, the Albumify config overlay only copies a profile knob when the name matches — so 15 of profile_4's 45 knobs silently evaporate before they ever reach the bridge. Result: more, smaller clusters than FC v2. No test caught it because every parity/equivalence test starts below the lossy layer.

5 · Why this is architectural, not a typo

A half-finished migration. The bridge's own docstring says it is "DEPRECATED — scheduled for deletion in spec-040 Phase 7," replaced by the unified chain (face_clustering_steps.py + FCAppRunner) that reads context.face_records directly. Phase 7 never landed, so the deprecated bridge is still the production Albumify path, while FC v2 already moved to FCAppRunner. The two apps diverged the moment FC v2 migrated and Albumify didn't — the bridge froze with an out-of-date, hand-maintained copy of the config mapping.
  • No single source of truth for FCParams→FCConfig. FC v2 has one (to_fc_config); the bridge re-implements it by hand and has drifted.
  • The overlay is lossy by construction. Name-matching against a schema that uses different names guarantees silent drops — there's no "unmapped knob" error, just a printed list nobody gates on.
  • Defaults that flip behavior. merge/split/attach=False in the bridge means Albumify skips whole stages FC v2 runs — the dominant cause of the count gap.

The structural gap: every parity test validates a layer where the names already agree. The lossy translation lives in the Albumify-specific overlay + bridge, and the one test aimed at it (test_config_parity) only ever fed it pre-matched inputs. No test runs a real profile end-to-end through both apps and compares cluster output.

7 · The fix direction (for discussion — not yet implemented)

  1. Delete the divergence, don't patch it. Make cluster_people (method face_cluster_knn) build its FCConfig via FCParams.to_fc_config() / FCAppRunner — the same single source of truth FC v2 uses — finishing spec-040 Phase 7.
  2. Pass profile_4 as FCParams, not as a name-matched dict overlay, so no knob can be dropped.
  3. Add the missing test: run a real profile through both apps' API entrypoints on Budapest2025_Google_14 and assert identical cluster sizes — the gate that should have existed.

Existing tool to reuse for the proof: face_cluster/config_diff.py already has effective_config_from_albumify(), effective_config_from_fc_config(), and compute() — run them on the real profile_4 (not hand-matched dicts) to print the field-by-field delta.
