Three kinds of "clustering" — and which one actually differs

You asked: are these pipeline elements? am I confusing this with image-level clustering? Answer below, with the code that proves it. Short version: you were right on both points.

Correcting my earlier claim

I said
Albumify runs a "legacy" face-clustering algorithm; FC v2 runs a "unified" one — two different algorithms.
Actually
They run the same face-clustering algorithm. Albumify's cluster_people is configured with method: face_cluster_knn, which calls the same run_face_cluster_knn bridge / FCConfig that FC v2 uses.
I conflated
cluster_by_identity (and the count I quoted, num_clusters) are image / scene level — exactly what you suspected. The face-identity count is a different number entirely.
Real gap
Config values (K=5 vs 51, blur_min=50 vs 150) + one extra refinement step — not algorithms.

1 · Yes — they are all pipeline steps. There are THREE clusterings.

The default Albumify pipeline (configs/pipeline.yaml → default_pipeline) is a flat list of steps. Three of them say "cluster", but they operate on two completely different things:

StepLevelInput → OutputWhat it groupsAlgorithm
cluster_scenes IMAGE scene_embeddings → scene_clusters Similar photos (same place/moment) HDBSCAN
cluster_by_identity IMAGE scene_clusters → face_subclusters Sub-divides scenes by face-count/identity (for photo selection) agglomerative
cluster_people IDENTITY face_embeddings → people_clusters Faces of the same person face_cluster_knn ← same as FC v2
discover_imagesscore_iqadetect_persons insightface_detect_facesfilter_facesalign_faces filter_quality extract_scene_embedding cluster_scenes extract_face_embeddings cluster_people identity_refinement cluster_by_identity select_best

IMAGE = scene/photo grouping  ·  IDENTITY = face/person grouping  ·  grey = producer/scoring steps

The number I misquoted: PipelineResult.num_clusters = len(scene_clusters) (pipeline_service.py:202) — that is the IMAGE count. The person count is the people table row count. So FC v2's "15 clusters" (identities) must be compared to Albumify's people count (~10–13), never to num_clusters (scenes, 6–16). My earlier table compared the wrong two numbers.

2 · The identity clustering is genuinely shared

Albumify's cluster_people step dispatches on a method key. The configured method is face_cluster_knn, which routes straight into the same bridge FC v2's unified chain uses:

cluster_people.py:200  elif method == "face_cluster_knn": → self._run_face_cluster_knn(...)
cluster_people.py:288  run_face_cluster_knn(faces, embeddings_norm, config, context)  (face_cluster_bridge.py)
face_cluster_bridge.py:146  def build_fc_config(config) -> FCConfig  ← face_cluster.config.PipelineConfig
face_cluster_bridge.py:167  FCConfig(K=config.get("K",5), distance_threshold=…, merge_*=…)

FC v2 builds the same FCConfig — it just gets its values from FCParams (profile_4.json) instead of the cluster_people: block of pipeline.yaml. Same algorithm, two config sources. That is the divergence.

3 · Where the numbers actually come from — config diff

Side-by-side of the knobs that move the person count. Same algorithm; different inputs → different clusters.

KnobAlbumify cluster_peopleFC v2 profile_4Effect
K (kNN neighbours)551Biggest driver — graph connectivity. 5 vs 51 changes who links to whom.
blur_min50150FC v2 drops blurrier faces → fewer, cleaner faces enter clustering.
distance_threshold0.350.35same
use_adaptive_merge_thresholdnot set (default off)trueFC v2 adapts merge cutoff by percentile; Albumify uses a fixed one.
attach_enabledfalsefalsesame (neither attaches inside the clusterer)

Plus one structural difference, not a config knob: Albumify runs an extra identity_refinement step after cluster_people, and the people table prefers its output — refined_people_clusters or people_clusters (pipeline_service.py:227). FC v2 (with profile_4) does not run that post-step. So even with identical config, Albumify's final person count can shift by the refinement's attach/reassign pass.

4 · What this means for spec-079 (much smaller than I implied)

  • No algorithm swap needed. Reaching FC v2's identity result is a config alignment: feed profile_4's flat knobs into the cluster_people step config (it already accepts the same K / distance_threshold / merge_* / blur_min keys — same shape as FCParams).
  • One real decision: does Albumify keep identity_refinement in the chain (it changes the final count vs FC v2), or do we exclude it for a true apples-to-apples baseline?
  • Baseline correction (Stage 0): the equivalence anchor compares FC v2's 15 identities to Albumify's people count, not num_clusters. The capture script must read the people table, and the run must pass profile_4 knobs into cluster_people.
  • The earlier "Stage 0.5: align the clusterer" worry is downgraded: there is no separate clusterer to align — only the config to pass through and the refinement step to decide on.
