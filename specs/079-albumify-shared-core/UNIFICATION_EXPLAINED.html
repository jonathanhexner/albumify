3 · The root cause — in one picture

The clustering code is identical. The two apps just feed it a different set of faces. The extra faces sneak in because pose data went missing.

sequenceDiagram
    participant Det as insightface detector
    participant Br as face_cluster_bridge
(Albumify only)
    participant FR as FaceRecord
    participant Gate as pose gate (yaw≤30, pitch≤25)

    Det->>Br: pose = [yaw,pitch,roll] LIST
key = forward/slash/path
    Note over Br: bug 1 · looks up by back\slash path → MISS
    Note over Br: bug 2 · reads 'pose_scores' dict → MISS
    Br->>FR: pose = None  (for EVERY face)
    FR->>Gate: face with no pose
    Note over Gate: permissive when pose absent →
passes 53 off-angle faces it should reject
    Gate-->>FR: core set 133 → 186
Figure 3 — Albumify's pose data never reached the gate. Two plumbing bugs: wrong path key + wrong field shape.
The 53 faces ARE the whole gap. FC v2's gate rejects 53 off-angle faces (46 yaw + 7 pitch). Albumify rejected zero — not because the knob was missing (it was set), but because FaceRecord.pose was None, so the gate had nothing to act on. Same images, same gate config, no input data.

How to read health: a module is good when both apps share it (engine, spec, producers, the 8-step chain) or it's correctly app-specific (persistence). It's amber when it's the right destination but only one app uses it yet (FCParams). It's bad when it's a duplicate/divergent path that must be removed (ClusterPeopleConfig, face_cluster_bridge.py).
Headline: Execution is unified and shipped (real progress). The product-visible goal — same config → same people — is not met yet (verified: 8 vs 20). The durable fix belongs in the detector, not the bridge. Do not commit the edited golden fixtures — they re-baseline "correct" to 13 and would bless a wrong state.
