Unified pipeline config — one contract, one runner, two apps

Make Albumify and FC v2 execute the pipeline identically given identical config. spec-079 · 2026-06-06

Goal. After this work, calling the pipeline from either app with the same configuration produces the same run — same faces gated, same clusters, same numbers. Today they don't: identical profile_5.json → FC v2 gives 8 identities, Albumify gives 20 (SIGHTING-096). The fix is to collapse the two config paths and the two clustering implementations onto the one typed contract and step chain that already exist.
The one-sentence diagnosis. FC v2 carries a typed FCParams (45 knobs) losslessly into the 8-step unified clustering chain; Albumify carries untyped dicts into a monolithic cluster_people step backed by a deprecated hand-rolled bridge that silently drops gates. The convergence target (unified steps + FCParams) is already built — Albumify was just never switched onto it (spec-040 Phase 7 unfinished).

1 · Situation today — ONE shared executor, divergent step-lists

Correction to an earlier draft: this is not two separate stacks. Both apps run the same PipelineExecutor over a step-name list + PipelineContext + PipelineConfig(step_configs: dict). The shared framework (executor, registry, context, and most steps) is well-built. The divergence is narrow: (i) which clustering step is in the list, (ii) how step_configs is built, and (iii) the orchestration wrapper around the executor call.

3 · Why it diverges — TWO layers

Key result (Stage 0b). Two independent layers. A · CONFIG 3 dropped/pinned quality gates: 8→10. B · PRODUCER CHAIN on identical face_records the bridge and the 8 unified steps cluster identically (FC v2 faces→10/86 both; Albumify faces→20/100 both) — so the clustering CODE is NOT the divergence. The 10→20 is the face set: FC v2's producer yields core 133, Albumify's yields 186. The fix is unifying the producer chain, not the clustering steps. See LOCALIZE_GAP.html.

Layer A — config (the 3 quality gates)

scripts/diff_fcconfig.py on profile_5: the two FCConfigs differ in exactly 3 fields, all quality gates.

CONFIGfixed for free once Albumify uses FCParams → to_step_configs → FaceClusterConfig(**config) (no hand mapping). PIPELINEneeds a real blur-scoring step in the shared producer chain.

Confirmation experiment (done). FC v2 with the 3 gates neutralized (profile_5_nogates.json): 10 clusters / 86 assigned — NOT 20. So the gates explain only 8→10. Re-running diff_fcconfig.py under nogates shows the configs are now behaviorally identical (lone residual min_face_area 0 vs None, both = no gate). Conclusion: the remaining 10→20 is Layer B — the producer chain (different face set), NOT the clustering code; Stage 0b proved bridge ≡ unified.

Layer B — producer chain (the face set), NOT the clustering code

Stage 0b ran both recipes on identical face_records — they match exactly. The divergence is the input:

The face sets differ because the producer chains differ: Albumify runs filter_faces + filter_quality + scene steps FC v2 doesn't, so a different face population / alignment / embeddings reach the clusterer → core 133 vs 186 → 10 vs 20. Pinning the exact producer step (Stage 0c) = diff the two face tables. NB: deleting the bridge is now cleanup (DRY), not the behavioral fix.
