Albumify → Shared Core: staged, verified, on Budapest

Every stage runs on D:\Budapest2025_Google with profile_4.json and is held to the Face-Clustering-v2 gold standard. Test → code-review → commit after each. Date 2026-06-05.

The spine of this plan: Albumify and FC v2 share the pipeline, so on the same album+profile they must produce the same clustering. We capture that as a frozen baseline once, then assert it still holds after every refactor stage. If a stage changes the cluster numbers, the stage is wrong — not the baseline.

Slim the people table to authored-only
delete the stale duplicate

Now that reads come from the view, retire the duplicated membership. The people table becomes a thin authored overlay — name, thumbnail override, merge-group — keyed to (run_id, cluster_id). This is the "proper" end-state the user asked about: clustering truth in the run-dir, human edits in a small table.

What we do
  • Alembic migration: keep name/thumbnail_*/add merge_group; stop writing face_instances (drop after a deprecation window).
  • create_from_clusters() no longer snapshots membership — it writes only authored defaults (or nothing until first edit).
  • Mutations (rename/merge/split) rewritten to operate on the overlay; merge = group cluster_ids, not copy faces.
  • Backend mutation round-trips + Playwright rename-persist + equivalence all green.

Risk controls baked into the order

  • Net before nails: Stage 0 freezes behavior; every later stage is measured against it, so a regression surfaces the moment it's introduced — not three stages later.
  • Dormant-then-wire: Stages 1–2 add fully-tested layers without touching the running app; only Stage 3 flips the read path, with the golden as a tripwire.
  • Schema change last among the data stages: the destructive people-table slim (Stage 4) happens only after reads already come from the view, so dropping face_instances can't break a read.
  • One commit per stage → trivial revert granularity if the code-review agent flags something post-hoc.
