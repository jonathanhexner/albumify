1 · What "baseline" means here

Before I start changing code (introducing the repository, moving the people reads, slimming the table), I run the app once and save its current output to a file. That saved output is the baseline — a "before picture."

Why: after each refactor step I re-run and compare to the before picture. If the numbers still match, the refactor didn't break anything. If they move, I caught a regression immediately. The baseline's only job is to be a stable reference — it does not need to be "perfect", it needs to be "what Albumify does today."

"The 20-baseline" was just my shorthand for "the before picture, which contains 20 people-groups." Sorry for the jargon.

3 · Is there a problem? Two separate questions.

Q1 — Does this block the refactor (the actual spec-079 work)? No
The refactor is about where data is read from (repository, views, people table) — not about how many people the clustering finds. The baseline only needs to be stable so I can detect regressions. 20 is perfectly fine for that. I can proceed today.
Q2 — Does Albumify match v2 exactly? Not yet (20 vs 15)
This is a real but separate issue, already logged as SIGHTING-094. Cause (very likely): Albumify's cluster_people step doesn't let you set v2's exemplar settings (N_exemplars_max, exemplars_d10_threshold, exemplar_suppression_radius). Merging relies on those exemplars, so without them Albumify merges less → more small groups. The fix is to expose those few settings — a small, contained clustering change, independent of the refactor.
