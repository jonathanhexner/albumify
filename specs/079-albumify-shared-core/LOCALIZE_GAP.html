What this changes in the plan

Re-scope. "Route Albumify's clustering onto the unified steps" does not fix the divergence — the two clustering paths already agree. The real work is unifying the producer chain so both apps feed clustering the same faces.
  • Layer A (config gates) — still real: 3 gates, 8→10. Fixed by the typed FCParams contract.
  • Layer B (was "code path") → actually the PRODUCER CHAIN — different face set (core 133 vs 186), 10→20. Fixed by running the same detect/filter/align/embed sub-chain in both apps.
  • Deleting the bridge / consolidating clustering steps stays worthwhile as cleanup (DRY, one path), but it is no longer the behavioral fix.

Stage 0c — the exact producer delta: POSE (resolved)

Named cause: the pose gate. Same images, same faces (340 vs 337), same gate. Rejection reasons diverge: FC v2 {pose_yaw: 46, pose_pitch: 7, top_k: 154} vs Albumify {top_k: 151}. FC v2 rejects 53 off-angle faces for pose; Albumify rejects zero — and 53 = 186 − 133, the entire core-set gap.

Root: FC v2's faces carry pose (yaw/pitch/roll, from insightface_detect_faces); Albumify's FaceRecord.pose is None (the "Pose gate: NOT WIRED" warning). With profile_5's limits (yaw≤30°, pitch≤25°) and require_pose=false, FC v2 drops the off-angle faces while Albumify's None-pose faces vacuously pass. The 53 survivors inflate the core set → 20 identities vs 8.
