Bringing Albumify onto the Face-Clustering v2 Core

How to make the Albumify web app share v2's data layers, contracts, and patterns — while keeping the Streamlit + FastAPI split. Date: 2026-06-05.

The headline: you are not missing a shared core — you already have one, and the API already builds it on every run. The same pipeline writes the same normalized run-directory database that v2 reads. The API simply throws that result away on read and re-derives its own denormalized copy. So this is an adjustment, not a rebuild: redirect the read path, unify the contracts, and adopt v2's UI patterns page by page.

1 · What's true today

Three facts decide everything. Each was confirmed by reading the modules, not guessed.

✅ The pipeline is already shared

Both apps run the identical engine: PipelineExecutor, the same step registry, and the same FCAppRunner clustering chain. Nothing to merge here.

API: sim_bench/api/services/pipeline_service.py
v2: app/face_clustering_v2/pipeline.py
both call: sim_bench/pipeline/executor + steps

✅ The normalized result is already written

Every API run ends in the face_cluster_export step, which calls RunExporter and writes runs/<id>/face_clustering.db — the exact tables v2's RunStore → repositories → views consume.

writer: sim_bench/run_db/exporter.py
reader: sim_bench/run_db/store.py

❌ The API ignores it on read, and serves a parallel shape

Instead of reading the run-directory DB back through v2's view layer, the API re-derives a denormalized people table into the central catalog DB and serves its own Pydantic schemas. Result: two databases, two contract shapes for the same "face", "cluster", and "person". Zero imports of run_db.store, face_cluster.repositories, or face_cluster.views exist anywhere under sim_bench/api/.

Why the catalog DB stays. The central sim_bench.db holds things v2 has no equivalent for and that are genuinely valuable: the multi-album catalog, the universal_cache embedding cache, user correction overrides, and the event log. That is an asset to keep — not debt to delete. A rebuild would force you to re-create it from scratch.

6 · The migration, phase by phase

Each phase is independently shippable. The app keeps working after every phase.

1

Promote the view dataclasses to the contract

Make face_cluster/views dataclasses the single source of truth, and generate the API's Pydantic schemas from them so no second hand-written definition exists. Fix the bbox/identity divergences here, once.

canonical: face_cluster/views/_base.py, _specs.py  ·  regenerate: sim_bench/api/schemas/face.py · people.py · result.py
2

Redirect API reads through RunStore → repositories → views

Rewrite the read endpoints to delegate to the view layer instead of querying the denormalized people table. Mutations (rename, merge, override) still write the catalog DB but key off the run-directory identifiers.

touch: sim_bench/api/routers/results.py · people.py · faces.py  ·  services/result_service.py · people_service.py
delegate to: face_cluster/repositories/ + face_cluster/views/cluster_analysis.py · face_metrics.py · image_metrics.py
3

Adopt v2 UI patterns in Albumify, page by page

Replace hardcoded st.slider bounds with UI_SPEC+widget_factory, and replace hand-built tables with ColumnSpec-driven rendering. Start with the table-heavy pages where the win is largest.

order: results.py → explore.py → face_management.py → configure.py
reuse: app/face_clustering_v2/ui_spec.py · widget_factory.py · face_cluster/views/_specs.py (ColumnSpec)
4

Lock it with a web-stack Playwright test

Mirror the Budapest gold-standard suite, but drive the FastAPI + Albumify web stack end-to-end (run pipeline → assert cluster count/sizes → exercise a correction). This is the regression net that makes the per-page swaps safe.

model on: tests/face_clustering/e2e_budapest/  ·  new: tests/streamlit/e2e_albumify/ (source D:\Budapest2025_Google, expect 15 clusters / 340 faces)

7 · The one decision that sets the scope

⚠ What happens to the denormalized people table?

This is the crux. Everything else follows from it, and it's a product/ops call as much as a technical one.

Option A — Retire it (serve live from views). The run-directory DB becomes the only source of truth for identity results; the API computes people on read. Cleanest end state, zero duplication. Cost: every user correction must round-trip into the run-directory layer's action log, and thumbnails/names need a home.
Option B — Keep it as a thin write/override cache. The people table stops being a result store and becomes only names, thumbnails, and override state — keyed to the run-directory as the source of truth. Lower risk, smaller blast radius, preserves the mutation flows as-is. Cost: a small amount of intentional denormalization remains.

Default recommendation: Option B. It keeps Phase 2 small and the corrections UX untouched, and you can still evolve toward A later. Confirm this before Phase 2 begins.

8 · Risks to plan around

Contract churn ripples. Phase 1 changes shapes (bbox tuple, identity naming) that both frontends read. Mitigation: land Phase 1 behind the generated-schema step and run both e2e suites before merge.
Run-directory availability. The API read path now hard-depends on the run dir existing on disk. Mitigation: keep RunStore's schema-version guard, and return a clean 409/"run not exported yet" instead of a 500 when a run is mid-flight.
Mutation/read split. Reads come from the run dir, writes go to the catalog DB — a correction must be reflected on the next read. Mitigation: Option B keeps overrides as an explicit overlay applied in the view-serialization step, so the merge point is one well-tested function.

9 · Definition of done

  • API read endpoints import and delegate to face_cluster.views — confirmed by an architecture test that fails if sim_bench/api re-introduces a parallel read path.
  • One contract definition per concept; API schemas generated from the view dataclasses.
  • Albumify config + tables rendered via UI_SPEC / ColumnSpec (no hardcoded slider bounds).
  • Green e2e_albumify Playwright suite on the Budapest gold standard.
