Configuration Contract — Where We Are, and Two Ways Forward

2026-05-23 · spec-041 follow-up · proposed by Jonathan Hexner: "one specification that everyone reads from"

1 · The bug you hit

You loaded profile_1.json, which contains yaw_max: 999.0 — the "disable pose gating" sentinel. The page crashed:

streamlit.errors.StreamlitValueAboveMaxError: The value 999.0 is greater than the max_value 90.0.
  ... in run_tab.py: yaw_max = st.slider("yaw_max °", 5.0, 90.0, 30.0, 1.0, ...)

Two layers disagreed on what was a legal yaw_max:

LayerSays yaw_max isWhere it lives
Validation (FCParams)any float in [5.0, 999.0]face_cluster/fc_params.py · Field(30.0, ge=5.0, le=999.0)
UI slider widgetany float in [5.0, 90.0]app/face_clustering_v2/tabs/run_tab.py · st.slider("yaw_max °", 5.0, 90.0, 30.0, 1.0)

The profile was legal by the validation contract but illegal by the UI widget. There were two sources of truth, and they drifted. That's the architectural problem; the crash was the symptom.

3 · Current architecture (the problem)

Today: two independent sources of truth for the same parameter. A profile that satisfies validation can be illegal in the UI.

4 · The goal: one specification

Your principle, rephrased: a parameter is defined once, in one document, including everything anyone needs to know about it — what it means, what values are legal, what range a UI should show, what its default is, and what widget type it deserves. Every consumer (validator, UI, profile loader, CLI, docs generator) reads from that single document.

Today the document is split: FCParams has the validation half; widget literals in run_tab.py have the display half; profile JSONs implicitly inherit from FCParams. Two halves are missing one of the consumers, so they drift.

5 · Option A — collapse to one range, drop the sentinel

Option A: one validation range (5–90), and "off" is a separate boolean field. The 999 sentinel disappears.

What changes

LayerChange
FCParamsTighten yaw_max/pitch_max/roll_max to le=90.0. Add pose_gating_enabled: bool = False.
FCConfigSame — add pose_gating_enabled; tighten ranges.
Algorithm codeQuality gater replaces "yaw_max >= 999 means off" with "if not pose_gating_enabled: skip". Cleaner semantics.
Run tab widgetStill hand-written; ranges now match FCParams by construction (because FCParams shrunk).
Existing profilesAnything with yaw_max=999 fails validation. Migration script needs to convert 999 → pose_gating_enabled=False.

Strengths and weaknesses

PRO Cleanest contract — no magic numbers, no UI/validation split.

PRO The 999 sentinel was always a code smell; this removes it.

CON Breaks existing profiles. profile_1.json as I wrote it is invalid under this option.

CON Doesn't solve the general problem — widget ranges are still hand-written in run_tab.py. If someone tightens FCParams.K's range tomorrow without touching the widget, drift recurs. This is the bigger structural concern.

CAVEAT Solves THIS class of bug (sentinel-vs-slider). Does not solve "two parallel sources of truth for ranges".

6 · Option B — FCParams owns validation and UI hints

Option B: validation bounds AND display hints both live in FCParams, side by side. The widget factory reads json_schema_extra and builds the right Streamlit control.

What changes

LayerChange
FCParamsEach field gets json_schema_extra={"ui_widget": ..., "ui_min": ..., "ui_max": ..., "ui_step": ..., "ui_help": ..., "ui_group": ...}. Validation ranges (ge/le) stay as-is.
FCConfigNo change.
Run tab200-LOC widget block collapses to a ~30-LOC loop over FCParams.model_fields, grouped by ui_group.
Profile JSONNo change. profile_1.json with yaw_max=999 still valid (Pydantic validation), still loadable (number_input has min=5, max=90 for display but accepts typed values up to 999).
Algorithm codeNo change. 999 sentinel still works.
NEW widget_factory.py~80 LOC. Reads model_fields[name], returns the appropriate st.<widget> call.
NEW arch test"Every UI-bound field has both ge/le AND ui_min/ui_max, and ui_min ≥ ge, ui_max ≤ le." Prevents drift at PR time.

Strengths and weaknesses

PRO One file is the single source of truth for everything user-facing about every knob.

PRO Solves the general problem — applies to every new field automatically, not just the three pose ones.

PRO Backward compatible: existing profiles still load, sentinels still work.

PRO The legacy FC App can adopt the same factory later — one widget block for both apps.

PRO Auto-generated docs become possible (docs/architecture/parameters.html from FCParams.model_fields).

CON More upfront work (~1.5h vs. ~15 min for Option A's hotfix).

CON Adds Pydantic-specific idiom (json_schema_extra) — slight learning curve.

8 · Recommendation

Your stated goal — "one specification that everyone reads from, this is true for any parameter in any GUI" — is exactly Option B. Option A solves the immediate yaw_max crash but leaves the general drift problem intact, and the 999-sentinel removal makes existing profiles incompatible.

Option B has the property you described: one file (fc_params.py) describes the whole user surface; everything else — the Streamlit UI, the CLI, the profile loader, future docs generators, future apps — reads from that file.

Concrete implementation plan if you sign off on Option B

  1. Extend FCParams — add json_schema_extra to every UI-bound field (~35 fields). The non-bound fields like d10_k, K_attach, etc. are left untouched and stay invisible to the UI.
  2. Write app/face_clustering_v2/widget_factory.py — one function render_field(name) -> value that builds the right st.<widget> call from the metadata. Grouping logic uses ui_group.
  3. Replace the run_tab.py widget block with a loop over FCParams.model_fields, grouped by ui_group.
  4. Add arch test tests/architecture/test_fcparams_ui_hints_consistent.py: every UI-bound field has both validation bounds AND UI bounds, and they're compatible.
  5. Update _profile_bar.py — the WIDGET_KEY_BY_FIELD dict goes away; the factory uses a deterministic key derived from the field name (f"v2_{name}").
  6. Add Playwright regression driving Load on a profile whose values sit at every range edge (the test that would have caught yesterday's crash).

Estimated effort: ~1.5 hours including the test. Net effect: run_tab.py drops from ~200 LOC to ~50 LOC; _profile_bar.py's mapping dict (35 lines) disappears; the legacy merge sub-panel (merge_controls.py) is unchanged in this step but can be migrated to the same factory later for full uniformity.

One ask before I proceed: the existing legacy FC App also has the same widget-literal pattern (app/face_clustering/tabs/run_tab.py + app/shared/merge_controls.py). Option B lets the legacy app eventually adopt the same factory. Should this spec target both apps now (more work, full uniformity), or just v2 now and legacy in a follow-up? I'd recommend just v2 first — get the pattern right, then migrate legacy when nothing's broken.
