spec-115 — Album workbench: run, re-run and examine albums, locally or on the L4

Status: In Progress (W1 done 2026-10-23) · Created: 2026-10-23 · Roadmap: Stage C, next, before Gate 1 · Split from: spec-112 Phase A2

Colour = type of change: NEW CHANGED REMOVED. Progress = ● done · ◐ partly done · ○ planned. In the class diagram: ✚ new member · ✎ changed · ✖ removed · unmarked = unchanged.

1. Objective

Start, watch, cancel and re-run album jobs from the Albumify app, on this PC or the Modal L4, and examine the results the same way either way. Photos go up once and never come back; re-runs reuse what was already computed. Gate 1 (judging the picks) is done in this app.

Open decisions / risks / non-goals

  • Decided (owner, 2026-10-23): photos kept on Modal 7 days after last use; re-run chooses the pipeline by name only.
  • Risk: crop orientation. Face boxes come from the worker's detector; the PC crop must read the photo the same way (EXIF orientation, rotated-face detection). Gate in R10: checked on a real job before the worker stops sending crops.
  • Risk: one cache writer. A SQLite cache on a Modal Volume is safe for one job at a time, so L4 jobs queue.
  • Risk: steps without a model version in their cache key rely on a model_name bump when their output changes; a cache that persists on the L4 makes forgetting that costlier.
  • Non-goals: moving old Modal job outputs (album files stay on albumify-jobs until spec-112 Phase B), jobs surviving an API restart, cloud DB/storage (spec-112 Phase B), user accounts, the public site.
