A1. Four-layer architecture CODIFY

What we have today

spec-042 H1 split History into four layers — DB access, App contracts (typed vocabulary), Backend service, Streamlit UI — with an arch test (test_v2_layering.py) enforcing that views/* doesn't import streamlit and tabs/* doesn't bypass services. It works.

The four-layer split established for v2. Layer 2 (contracts) is a shared vocabulary both layer 3 and layer 4 import; everything flows top-down except contract definitions.

Why it matters going forward

This is the structural decision that everything else assumes. Without it: the FastAPI handlers, the headless CLI, the future React/Qt frontend, and the tests all end up duplicating service logic. With it: any new surface plugs in at layer 3 (call the service) without re-implementing the data access. The arch test catches drift at PR time.

What to codify

Move the four-layer description from spec-042 §4.1 into docs/architecture/overview.md as a top-level "Repo Layering" section. Every new feature spec references it and identifies which layers it touches.

A2. Declarative specs over repetitive code CODIFY

What we have today

Two examples working well today:

  • UI_SPEC (spec-041): per-FCParams-field widget metadata (label, group, order, step). The widget factory iterates over it. Zero hand-written widgets for parameter inputs.
  • ColumnSpec (spec-042): per-column metadata (field, label, fallback, formatter). The table renderer iterates over it. Zero hand-written column extraction code.

The legacy History tab had 16 lines like st.text(f"K: {cfg.get('K', '?')}"). v2 replaces those with one iteration over UI_SPEC.

Why it matters going forward

Every new piece of UI metadata follows this pattern. Examples already on the horizon:

  • Cluster Analysis tab: ClusterCardSpec (which face thumbnails, what stats line, what action buttons).
  • Face Analysis tab: FaceFieldSpec (which scores to display, in what order).
  • Filter chips: FilterChipSpec (the chip text + the predicate it applies).

The principle generalizes: when you see a list of "field name + how to display it" appearing as code, replace with a list of typed spec objects + one renderer.

Before / after pattern

// before
def render_summary(row):
    st.text(f"K: {row.K}")
    st.text(f"distance_threshold: {row.distance_threshold}")
    st.text(f"min_cluster_size: {row.min_cluster_size}")
    # ... 13 more lines, each duplicating a field name

// after
SUMMARY_FIELDS = [ColumnSpec("K", "K"), ColumnSpec("distance_threshold", "Threshold"), ...]
def render_summary(row):
    for spec in SUMMARY_FIELDS:
        st.text(f"{spec.label}: {spec.display(row)}")

What to codify

Add to CLAUDE.md §Coding: "When you write three lines that all look like do_something(field_X) with only the field name varying, stop. Define a typed spec; have one function iterate over it. See UI_SPEC / ColumnSpec for prior art."

A3. Three-layer testing pyramid CODIFY

What we have today

spec-042 H1 ships with:

  • 31 service unit tests against synthetic data — in-memory SQLite seeded by _seed.py factories. Runs in ~1.7s. The load-bearing layer.
  • 4 real-fixture smoke tests — against the actual ~/.sim_bench/sim_bench.db. Skips cleanly when the file is absent (CI). Catches schema-drift surprises.
  • 1 Playwright UI smoke test — opt-in, manual, screenshot-captured. Catches widget-binding regressions that pass unit tests but break visual rendering.

Why it matters going forward

The three layers protect against three different failure modes. Without all three:

  • Skip synthetic → tests are slow, depend on the dev machine, and edge cases are hard to construct.
  • Skip real-fixture → schema-drift surprises ship to prod.
  • Skip UI smoke → widget-binding regressions (like spec-041's yaw_max=999 crash) slip through despite green unit tests.

The pyramid is well-understood for backend code; this codifies it for UI-bound code too.

What to codify

Add to docs/guides/TESTING_RULES.md the three-layer pattern as a binding standard for any new feature that touches a UI tab or a backend service. Reference HISTORY_TAB_PRD.md §8 as the canonical example.

A4. Architecture tests are part of every spec CODIFY

What we have today

Five arch tests exist now, each guarding a different drift class:

  • test_fcparams_fcconfig_parity.py — FCParams and FCConfig field sets stay in lockstep
  • test_ui_spec_references_fcparams.py — UI_SPEC entries reference real FCParams fields
  • test_logging_aligned.py — every entry point calls setup_logging with the right surface name
  • test_v2_layering.py — face_cluster/views/* doesn't import streamlit; tabs/* doesn't bypass services
  • test_v2_module_docstrings.py — every public class/function has a docstring

Each was added during the spec that introduced the constraint. The pattern: codify the architectural invariant as a test at the moment you create the invariant.

Why it matters going forward

An invariant without a test is documentation, not architecture. Six months from now nobody remembers the rule; the test does. The investment cost is low (typically <50 LOC per test) and the cost of NOT having it is real (every drift we've fixed in spec-040/041/042 surfaced as a CI failure exactly because some prior author wrote the test).

What to codify

Add to WORKFLOW.md as a phase-0-of-every-spec checkpoint: "List the architectural invariants this spec introduces. For each, write the arch test before the implementation. The test goes in tests/architecture/test_<spec_concern>.py." Add to the Code Review checklist §5 the explicit question: "For every constraint described in this spec, name the test that would fail if it were violated."

A5. Documentation contract CODIFY

What we have today

spec-042 introduced binding rules for new v2 code: every public class/function has a docstring; functions over 30 LOC must be split; no fc1, fc2, fc3 placeholder variable names; no ASCII section dividers; render_* functions document what they read and write. Enforced by test_v2_module_docstrings.py; legacy files on an allowlist.

Why it matters going forward

The arch test only checks presence, not quality. That's deliberate: reviewers handle prose; the test handles "did you remember to do it at all". Going forward we need a story for the allowlist — pre-existing files that didn't ship docstrings get retired from the allowlist as they're touched.

What to codify

Two rules:

  1. Allowlist shrinks monotonically. When a legacy file gets modified (not just trivial edits — meaningful refactors), the modifier is responsible for either documenting its public surface or removing it from the allowlist with a justification.
  2. New code is never added to the allowlist. If a new module needs a docstring exemption, the spec must justify it.

Add both rules to CLAUDE.md §General + the Code Review checklist §7 (documentation).

A6. Per-tab migration discipline — three architectural-layer tests + working code throughout CODIFY

What we have today

spec-042 H1 (History tab) followed this discipline implicitly:

  • Migration is one tab at a time. v2 grew from 2 tabs → 3 tabs in a single commit (807053c).
  • Legacy app/face_clustering/main.py (~11 tabs) stayed runnable throughout. Untouched.
  • v2 app/face_clustering_v2/main.py stayed runnable at every intermediate state — H1, H2, H3 each ended green.
  • Tests landed at three architectural layers: service unit + real-fixture + Playwright UI smoke.

The "tab-by-tab while never breaking either app" is the strangler-fig pattern made operational. The "three architectural-layer tests" is what proved each tab actually works against its own data, not just compiles.

Why it matters going forward

Seven tabs remain to migrate in spec-042. Without this discipline made explicit:

  • Someone batches multiple tabs in one PR, gets stuck on one, and now nothing ships.
  • Tests get written at the layer the author thinks is "enough" — usually UI smoke or service alone. The other layer's bugs ship.
  • A migration breaks the legacy app silently (someone accidentally edits a shared module) and is only noticed days later.

With it: every tab migration is a small, complete, independently-shippable unit. Each PR is a checkpoint where both apps run, all tests pass, and the new tab is fully covered at every layer it touches.

The standard

The three-layer test gate

Every tab migration ships with tests at three architectural layers:

The incremental-migration rule

Three sub-rules, all binding:

  1. One tab per commit (or PR). Never batch unrelated tabs. Each tab migration is its own atomic unit.
  2. Legacy app stays runnable at every commit. .venv/Scripts/streamlit run app/face_clustering/main.py must work after the merge. The legacy app is the safety net — it's how a user gets unblocked if v2 has a regression.
  3. v2 app stays runnable at every commit. Whatever tabs have been migrated, the v2 app loads cleanly and shows them. No commit may break a previously-shipped v2 tab.

B0. Repository pattern — persistence as classes, not free functions FIX

What we have today

Two modules underneath every view service:

face_cluster/run_history.py       — 154 LOC, 3 public free functions
face_cluster/run_history_db.py    — 457 LOC, ~12 public free functions

Both follow the same shape: every public function takes an optional db_path: Optional[Path] = None, opens a connection, queries, closes. The "which DB" is conceptually shared state pretending to be a per-call argument. Then HistoryService wraps them like this:

class HistoryService:
    def __init__(self, db_path=None):
        self._db_path = db_path

    def list_runs(self, query):
        return run_history.search(filters, db_path=self._db_path)

    def update_comment(self, run_id, comment):
        return run_history_db.update_comment(run_id, comment, db_path=self._db_path)
    # ...threads self._db_path to every call

That's 6 module-level functions taking the same argument from one instance variable. The Service is papering over what should be the lower layer's responsibility.

The deeper issue this surfaces

spec-042 §4.2 declares "every backend service is a class with typed methods" as the standard. But the layers underneath the standard — run_history + run_history_db — don't follow it. The inconsistency causes three observable problems:

  1. The from X import get_db_path trap. run_history.py binds get_db_path at import time. Monkeypatching the source module misses this binding. We tripped on this in spec-042 H1 — half the integration tests passed for the wrong reason. A class with self._db_path has no such trap.
  2. Test fixtures need workarounds. The session fixture in tests/face_clustering/conftest.py monkeypatches one of two get_db_path bindings. Real-fixture tests have to bypass it with explicit db_path= kwargs. The workaround is invisible — future tests won't know to do this.
  3. Composability is awkward. A future ClusterAnalysisService will need to query both the global action_log AND a per-run face_clustering.db. With free functions, that's two parallel sets of free-function modules. With Repository classes, it's two injected dependencies — straightforward.

The standard

Three rules:

  1. Persistence layer is a class, not module-level free functions.
  2. Constructor takes a typed Config dataclass, not individual kwargs. Adding a new option = adding a field to the Config; existing callers unchanged.
  3. Query methods take composable criteria (typed dataclass with optional fields). Adding a new filter axis = adding a field to the criteria; no new method needed.
# face_cluster/repositories/run_history_repo.py

@dataclass(frozen=True, slots=True)
class RunHistoryRepoConfig:
    """Repository constructor configuration. Every field has a default,
    so adding a new field is non-breaking for existing callers."""
    db_path: Optional[Path] = None
    auto_migrate: bool = True
    read_only: bool = False
    log_queries: bool = False
    connection_timeout_s: float = 5.0


@dataclass(frozen=True, slots=True)
class RunHistoryCriteria:
    """Composable filter for run history queries. AND across fields."""
    ids: Optional[list[int]] = None
    parent_run_id: Optional[int] = None
    album: Optional[str] = None
    status: Optional[str] = None
    producer: Optional[str] = None
    date_from: Optional[date] = None
    date_to: Optional[date] = None
    text: Optional[str] = None
    text_fields: tuple[str, ...] = ("album", "run_name", "comment")
    limit: int = 500
    offset: int = 0
    order_by: Literal["started_at_desc", "started_at_asc"] = "started_at_desc"


class RunHistoryRepository:
    """Read + write access to the action_log table. Thin SQL wrapper.
    Knows the schema; knows nothing about views, Streamlit, or services."""

    def __init__(self, config: Optional[RunHistoryRepoConfig] = None):
        self._config = config or RunHistoryRepoConfig()

    # Composable query API
    def find(self, criteria: RunHistoryCriteria) -> list[RunRow]: ...
    def find_one(self, criteria: RunHistoryCriteria) -> Optional[RunRow]: ...
    def count(self, criteria: RunHistoryCriteria) -> int: ...
    def distinct_albums(self) -> list[str]: ...

    # Convenience for the common single-id case
    def get_by_id(self, run_id: int) -> Optional[RunRow]:
        return self.find_one(RunHistoryCriteria(ids=[run_id]))

    # Mutations — named verbs per B3
    def start_action(self, action_type: str, payload: dict) -> int: ...
    def complete_action(self, action_id: int, result: dict) -> None: ...
    def fail_action(self, action_id: int, error: str) -> None: ...
    def update_comment(self, action_id: int, comment: str) -> None: ...

Then the Service composes the Repository:

# face_cluster/views/history.py
class HistoryService:
    def __init__(self, repo: Optional[RunHistoryRepository] = None):
        self._repo = repo or RunHistoryRepository()

    def list_runs(self, query: HistoryQuery) -> list[RunRow]:
        criteria = RunHistoryCriteria(
            album=query.album, date_from=query.date_from,
            date_to=query.date_to, text=query.text,
        )
        return self._repo.find(criteria)

Why typed Config + criteria, not kwargs or dicts

Same principle as A2 (declarative specs) and B4 (typed boundaries): when an interface might grow, the typed object IS the interface; the consuming methods stay stable. Imagine adding cache_strategy, retry_policy, read_only, connection_pool_size to the Repository constructor over time. With explicit kwargs, every consumer (services, CLI, tests) gets touched each time. With a Config dataclass, none change unless they care about the new field.

Two arch tests for spec-043:

def test_repositories_take_typed_config():
    """*Repository classes either take no args or one positional/keyword
    arg that's a frozen dataclass. Forbids growing kwarg lists."""

def test_repositories_have_no_module_level_free_functions():
    """face_cluster/repositories/*.py exposes only classes, dataclasses,
    and module-level constants. Forbids the legacy free-function shape."""

Why "Repository" is the right name

The pattern is well-established in layered architectures (DDD, .NET, Spring). A Repository:

  • Owns persistence I/O (SQL, file system, network)
  • Returns typed domain objects (not raw rows or dicts)
  • Knows the schema, nothing else
  • Has no awareness of views, services, or business rules
  • Is the only layer that imports sqlite3 / requests / etc.

Service composes one or more Repositories. UI composes Service(s). Tests inject test-double Repositories.

The transformation

AspectBeforeAfter
Persistence shape~600 LOC module-level functionsRunHistoryRepository class, same LOC
Test setupHistoryService(db_path=tmp) + autouse session monkeypatchHistoryService(repo=RunHistoryRepository(db_path=tmp))
Test isolationReal-fixture tests bypass with explicit kwargsTest repo and real repo are different instances; no monkeypatch needed

Layer ownership of db_pathShared between Service and module functionsRepository owns it; Service composes

Why it earns its keep going forward

Every future tab will have one or more services that need persistence. Without Repository:

  • Each Service threads db_path to every underlying call (boilerplate).
  • Each Service repeats the "translate query dataclass → filters → call free function" pattern (boilerplate × 3).
  • Each new persistence module repeats the "shadowed import" trap.

With Repository:

  • Service holds one or more self._repo instances.
  • The "which DB" question is answered once at construction.
  • Tests inject a test-double or temp-DB-backed repo.
  • Future surfaces (FastAPI, CLI) compose the same Repositories without touching the Services.

What this looks like as a spec

This is the right scope for spec-043 "Repository pattern for face_cluster persistence". Scope:

  1. Create face_cluster/repositories/run_history_repo.py (or similar location) consolidating run_history.py read functions + run_history_db.py CRUD functions into one RunHistoryRepository class.
  2. Migrate HistoryService to inject a repository via constructor.
  3. Migrate the ~6 legacy app call sites in app/face_clustering/ that still call the free functions directly.
  4. Update the session fixture in tests/face_clustering/conftest.py — likely simpler or removable.
  5. Add arch test: "persistence-layer modules must expose Repository classes; module-level free functions returning DB rows are forbidden."
  6. Document the pattern in the architecture standards and reference it from CLAUDE.md.

Effort: ~4-6h. Should be done before the next tab port (Cluster Analysis) so the second Service builds on the right foundation, not a workaround.

B1. Constructor injection; no shadowed module imports FIX

What we tripped over

During spec-042 H1 testing, the session fixture in tests/face_clustering/conftest.py monkeypatches run_history_db.get_db_path to redirect to a temp DB. Worked for one code path; failed for another.

Root cause: face_cluster/run_history.py binds get_db_path at import time:

from face_cluster.run_history_db import get_db_path  # ← capture original function

After the monkeypatch, run_history_db.get_db_path points at the temp DB, but run_history.get_db_path (the local binding) still points at the original. Result: search() hit real data while list_actions() hit temp data. Half the integration tests passed by accident.

Why it matters going forward

This is a class of bug, not a one-off. Any module that imports a function by name from another module captures the binding at import time. The pattern is unsafe for anything we want to test-double or environment-swap.

The standard

Two rules:

  1. Functions used as injection points are called via module-attribute access: run_history_db.get_db_path() not get_db_path() after a top-level import. The module attribute always reflects the current binding.
  2. For services / classes that need configurable dependencies, use constructor injection. Pass db_path, now(), logger, etc. as __init__ parameters with sensible defaults. HistoryService(db_path=...) is the pattern; every new service does the same.

What to do

  • Patch face_cluster/run_history.py to use run_history_db.get_db_path() instead of the bound name. ~3 line change.
  • Add an arch test test_no_shadowed_injection_points.py: scan for from X import get_db_path-style imports in modules whose tests monkeypatch the original module. Catches future occurrences.
  • Document the pattern in CLAUDE.md §Coding.

B2. Error model standardization FIX

What we have today

HistoryService raises plain ValueError for three distinct conditions:

  • Not found: get_run_detail(999999) → "No run with id=999999"
  • Validation: update_comment(id, "x" * 2049) → "Comment exceeds 2048 characters"
  • State conflict: load_run(id) when status != "complete" → "Run X is not complete"

The caller can't distinguish these without string-matching the message. The UI shows them all as the same generic error. In FastAPI handlers (if we add some), they all become HTTP 500 instead of the right 404 / 400 / 409.

Why it matters going forward

Every service we add has the same three categories. Without a standard, each service either invents its own exception hierarchy (inconsistent) or piles everything onto ValueError (lossy). The UI then has to interpret strings to render appropriate UX (e.g., 404 should show "this run was deleted" while a conflict should show "this run isn't ready yet").

The standard

One small hierarchy in face_cluster/views/_errors.py:

class ServiceError(Exception):
    """Base for all view-service errors. Carries an optional public message
    safe to display to end users."""
    def __init__(self, message: str, *, user_message: Optional[str] = None):
        super().__init__(message)
        self.user_message = user_message or message

class NotFoundError(ServiceError):
    """Requested entity does not exist."""

class ValidationError(ServiceError):
    """Inputs don't satisfy the contract (length, type, range, ...)."""

class ConflictError(ServiceError):
    """State precondition not met (e.g., trying to load an incomplete run)."""

class PermissionError(ServiceError):
    """Reserved for future ACLs."""

What changes per service

Concrete migration for HistoryService:

// before
raise ValueError(f"No run with id={run_id}")
raise ValueError(f"Run {run_id} is not complete ...")

// after
raise NotFoundError(f"No run with id={run_id}")
raise ConflictError(f"Run {run_id} is not complete ...")

The UI layer gets one try / except ServiceError in each tab and renders user_message appropriately. A future FastAPI surface maps NotFoundError → 404, ValidationError → 400, ConflictError → 409 with no logic per endpoint.

What to codify

Document the hierarchy in face_cluster/views/_errors.py docstring + reference in CLAUDE.md. Add to the service contract in spec-042 §4.2: "Services raise from ServiceError subclasses, never plain ValueError / RuntimeError."

B3. Service vocabulary (CRUD-like naming) FIX

What we have today

HistoryService happens to follow good naming: list_* for queries, get_* for single-entity reads, update_* for mutations, load_* for composite reads with side effects on disk. Nothing forces future services to do the same.

Why it matters going forward

When eight tabs all have services and someone needs to find "give me a list of X filtered by Y", they should be able to predict the method name. Today they'd grep; with a standard they read it off the contract.

The standard

Five verb prefixes, each with explicit semantics:

PrefixSemanticsSide effects?Example
list_*Return zero+ entities matching a queryNolist_runs(query) → list[RunRow]
get_*Return exactly one entity by id; raise NotFoundError if absentNoget_run_detail(id) → RunDetail
create_*Insert a new entity; return its typed representationYes (DB write)create_profile(spec) → Profile
update_*Mutate an existing entity; raise NotFoundError / ConflictErrorYes (DB write)update_comment(id, text)
delete_*Remove an entity; idempotentYes (DB write)delete_run(id)

Composite operations that don't fit (e.g., load_run = read + filesystem) get named with a meaningful verb but documented as composite: "Reads from DB + filesystem; does not mutate persistent state but constructs a new in-memory object."

What to codify

Add to spec-042 §4.2 + WORKFLOW.md's spec template. Code review checklist §3: "Service methods named per the five-verb taxonomy. Composite operations explicitly documented as such."

B4. Shared type definitions live in face_cluster/types.py FIX

What we tripped over

LoadedRun.pipeline_result: Any. The real type is face_cluster.pipeline.PipelineResult. face_cluster/views/history.py can't import it without creating a back-edge from a lower layer (views) to a higher-level module (pipeline). So we punted to Any and documented it in the PRD as an open question.

Why it matters going forward

This will happen again every time a view service needs to expose a return value whose canonical type lives in a higher layer. Any loses IDE autocomplete, mypy checks, and structural clarity. It's a future bug magnet.

The standard

One rule: any type used at a layer boundary lives in face_cluster/types.py (or a sibling shared module), not in the module that produces it. Today face_cluster/types.py already holds FaceRecord, ClusterResult, GraphResult — the pattern is established; we just need to extend it to PipelineResult.

What to do

  • Move PipelineResult from face_cluster/pipeline.py to face_cluster/types.py. ~10 lines moved, no behavior change.
  • Update LoadedRun.pipeline_result to the real type.
  • Document the rule in face_cluster/types.py's module docstring.

C1. Pipeline-of-operations as a reusable building block ADOPT

What we have today

spec-040 built sim_bench/pipeline/ — a domain-agnostic step framework: each step has typed requires/produces metadata, the executor logs per-step in/out (spec-041 follow-up), the registry resolves dependencies. It's currently used only by face clustering, but architecturally it's general.

The step framework is currently used only by face clustering, but its design is domain-agnostic. Each step is "give me these context keys, I'll write these context keys" — applies to any pipeline.

Why it matters going forward

Several future features map naturally onto a pipeline of operations but don't get to use the framework today because nothing's documented:

  • Run loading: load_pipeline_result is a 5-stage operation (validate dir → read DB → read embeddings → reconstruct → return). Could be a tiny pipeline.
  • Bulk export: a future "export all clusters as ZIP" operation.
  • Migration tooling: a multi-step "migrate legacy → current" operation.
  • Test data builders: the _seed.py factories could compose as pipeline ops.

For each of these, hand-rolling a sequence costs ~40 LOC; using the pipeline framework costs ~10 LOC + you get telemetry, dependency resolution, and error reporting for free.

What to codify

  • Document the pipeline framework as a reusable pattern, not just a face-clustering thing, in docs/architecture/pipeline_framework.md.
  • Add a "When to reach for the pipeline framework" decision matrix: "if your operation has 3+ sequential stages with named inputs/outputs, use it."
  • Refactor load_pipeline_result as a small example. This is the proof-of-concept that the framework works beyond clustering.

C2. Forward-only idempotent migrations ADOPT

What we have today

Two examples of migration logic:

  • DB schema migrations (face_cluster/run_history_db.py): idempotent ALTER TABLE pattern — check if a column exists; add it if not. Forward-only. Survives multiple invocations. Works.
  • Profile-format migration (scripts/migrate_fc_profiles.py): one-shot loader that backs up .v1.json + rewrites in the new shape. Idempotent (backup-presence detection). Works.

Two different shapes; two different conventions. No standard.

Why it matters going forward

Several things in this repo evolve their on-disk format over time: face_clustering.db schema, run profiles, action_log columns, output dir contents. Today every migration is bespoke. With a standard pattern, the next migration is a fill-in-the-blanks template.

The standard

One pattern, three rules:

  1. Forward-only: no rollback. Migrations move data from format N to N+1; reverse goes through restore-from-backup.
  2. Idempotent: running the migration twice produces the same end state as running it once. Either via "is current shape?" detection or via the "have I migrated this already?" marker (backup file presence, schema version column, etc.).
  3. Backup before mutate: every destructive migration writes a backup of the prior state alongside the new one. Backup is the rollback story.

Pattern template:

def migrate_one(thing) -> Literal["migrated", "already_current", "invalid"]:
    if not parseable(thing): return "invalid"
    if is_already_current(thing): return "already_current"
    backup(thing)
    convert_in_place(thing)
    return "migrated"

What to codify

Document in docs/architecture/migrations.md with the two existing examples (DB schema, profile JSON) as canonical references. Add to CLAUDE.md §General: "When changing the shape of persisted data, the migration follows the forward-only / idempotent / backup pattern."

C3. Service-level telemetry mirroring step in/out ADOPT

What we have today

Pipeline steps log a uniform in[...] -> out[...] (Xms) line per step (spec-041 follow-up). Diagnosing a pipeline failure is one grep. Service methods don't have an equivalent.

Why it matters going forward

When a Streamlit tab does something unexpected, the post-mortem question is: "what did the service return / raise?" Today: read the source, infer. With service-level telemetry: read the log.

The standard

A simple decorator added to every service method:

@logged_service_method
def list_runs(self, query: HistoryQuery) -> list[RunRow]:
    ...

// emits (at INFO):
// HistoryService.list_runs(query=HistoryQuery(album='Budapest')) -> 8 results (4ms)
// HistoryService.update_comment(run_id=42, comment='[34 chars]') -> None (2ms)
// HistoryService.get_run_detail(run_id=99) -> NotFoundError: No run with id=99

The decorator inspects:

  • Method name + class
  • Arguments (with long string redaction)
  • Return: shape (list length, dataclass name, or None)
  • Or the exception type and user_message (if a ServiceError)
  • Elapsed wall-clock

Why it earns its keep

For free, every service call appears in logs/<ts>/<surface>.log (the aligned logging from spec-041). When the user reports "the Load button didn't do anything," we look at the log and see exactly what arguments the click triggered, what the service returned, and whether session_state got written. No instrumentation per tab.

What to codify

Add the decorator to face_cluster/views/_telemetry.py; wrap every *Service method going forward. Document in spec-042 §4.2's service contract as binding.

C4. Visual mockup before code ADOPT

What we have today

HISTORY_TAB_PRD §3 has an ASCII mockup of the full History tab layout. It anchored the implementation: every section in the mockup corresponded to a component in the rebuild. No "what should this look like" debates during coding.

Why it matters going forward

Spec drift is the #1 cause of "I built it but it doesn't look like the user wanted." A mockup in the spec resolves the visual contract before the implementer touches Streamlit. Reviewers can react to the mockup; the implementer treats the mockup as the spec.

The standard

Every UI-touching spec includes an ASCII mockup of every tab/page/region it adds. The mockup shows:

  • Section headers + dividers
  • Widget placements (column layout, expander state, button positions)
  • Sample data shape (not full content, but enough to convey what fields populate which slot)
  • Interaction notes ("clicking row → opens detail below")

ASCII is preferred over screenshots/PNGs because (1) it's diffable, (2) it's editable in markdown, (3) it forces clarity at the conceptual level (which sections exist, which order) rather than pixel-level.

What to codify

Add to WORKFLOW.md's spec.md template: "If the spec touches UI: include a §3 Visual Specification with an ASCII mockup per region." Add to Code Review §7 the explicit question: "For each UI region in the spec, can you point at the mockup that anchored it? If not, that's spec drift."

Closing thoughts

None of these are revolutions. Each item is a small refinement to a pattern that already works on one example (FCParams, ColumnSpec, step telemetry, idempotent ALTER) and generalizes it to "this is how we do this kind of thing." The win is compounding: every future tab / service / migration / arch test follows a documented pattern instead of inventing one.

Suggested implementation slot: spec-043 — "Architecture Standards Codification." A documentation-heavy spec with small enabling code changes:

  • A1–A5: documentation updates (CLAUDE.md, WORKFLOW.md, docs/architecture/overview.md, docs/guides/CODE_REVIEW_CHECKLIST.md). ~3 hours.
  • B1–B4: code defect fixes + arch tests. ~4 hours.
  • C1–C4: new patterns documented + at least one concrete example per pattern. ~6 hours.

Net: ~13 hours over 1-2 days. Pays back on the next eight tabs in spec-042 plus everything after.

If we don't do this: every future spec re-invents the same decisions. The History tab pilot was deliberate about its patterns — the next tab could be sloppy without anything catching it. Codification keeps the architectural decisions enforced at PR time.
