SIGHTING-091: Streamlit st.dataframe row-pick is invisible to Playwright

Status: OPEN Medium severity
Reported: 2026-05-30 (after spec-063/064/065 v2 tab additions)
Blast radius: Blocks 5 of 6 budapest e2e scenarios (B, C, D, E, F). Does NOT affect the real product — users in a browser click rows fine.
Branch: unification/spec-040 · Last commit: f914e80

1. TL;DR

The v2 History tab renders the runs list as a modern st.dataframe with on_select="rerun". That widget is built on glide-data-grid — a canvas-rendered virtualised grid. It does not expose its cells via standard ARIA gridcell role with the cell text as the accessible name. So the budapest e2e scenarios all timed out on: 

page.get_by_role("gridcell", name="6437d335").first.click(timeout=15_000)

The cell is visible (screenshots in tests/face_clustering/e2e_budapest/_failure_artifacts/ prove it). It is just not addressable by Playwright role-based selectors. The user-facing app is not broken; the e2e test harness can't drive the row-pick step.

5. Why this is hard (the deeper mechanism)

LayerHow it worksWhy Playwright can't see it
st.dataframe (Streamlit Python API) Sends the DataFrame as JSON to the frontend (transparent — Playwright doesn't talk to Python)
streamlit/elements/lib/dicttools.js (frontend) Mounts the React <DataFrame> component (React tree is in the DOM)
glide-data-grid (npm) Paints rows + cells onto an HTML <canvas> element for performance — virtualises so only visible rows render 🔴 Canvas content has no DOM nodes. ARIA gridcell elements are not emitted per-cell. The cell text is rasterised pixels, not text the accessibility tree can read.
What the DOM does expose One <canvas> element with some loose ARIA wrappers around it. Row-checkbox column exists but with cryptic labels. get_by_role("gridcell", name="6437d335") finds zero matches; get_by_role("cell") would too.

6. Resolution options

Three viable paths, ranked by long-term value. The middle path is the narrowest; the first path is the most principled.

#ApproachEffortProsCons
A Replace st.dataframe(on_select) with a DOM-native row-pick widget
— e.g. st.radio with a row-per-option label, or st.button per row inside a grid, or a Streamlit data_editor with row-keys exposed as HTML.		 ~1 day
UI change
  • Makes the History tab e2e-testable by construction.
  • Also helps screen-reader users (real a11y improvement).
  • Catches the next 4 scenarios for free.
  • Pattern reusable in actions_table.py and any future tabular tab.
  • Loses the column sort / resize that st.dataframe ships.
  • Slight visual regression — less polished than glide-data-grid.
B Find a Playwright selector that addresses glide-data-grid cells
— empirically. Glide may expose the row-select checkbox column as a focusable element with a label like "Row N", or row-bounding-box hit-testing via coordinates may work.		 ~half-day
investigation
  • No UI change.
  • Keeps the polished dataframe widget.
  • Brittle — Streamlit / glide upgrades can break it.
  • Doesn't help screen-reader users.
  • Selectors will need to be re-found for every dataframe instance.
C Bypass the click; drive selection via Streamlit's AppTest API
at.dataframe(0).select_row(1) instead of page.get_by_role("gridcell", ...).click().		 ~2 h
test refactor
  • Already known to work — used in test_v2_app_smoke.py.
  • Faster (no browser).
  • 🔴 Loses browser-level coverage — this is the layer where the v2_K duplicate-key crash hid.
  • Doesn't reproduce real-user mouse + paint behaviour.
Recommended (chosen — see spec.md): C, refined — bypass the ONE click via a query-param seed in main.py; keep st.dataframe. The untestable surface is a single click. Everything after it (5 downstream tabs and their components) renders as standard DOM and is fully Playwright-addressable. We don't lose that coverage. We do lose visual wiring of "row click + Load button → service call", which the existing AppTest smoke (test_history_tab_recognizes_v2_run_as_loadable) + HistoryService unit tests on synthetic fixtures already cover.

Why not option A? Replacing st.dataframe with st.radio changes real UI for a benefit only the test harness sees. User pushed back on the earlier draft: "we could use a test that targets the endpoints… of course we don't get the same coverage, but it'll be reasonable." Correct call — option C-refined is ~2 h, zero UI change, same e2e value.

Production side-benefit: the query-param seeder makes ?current_run_dir=<path> a shareable deep-link. Free feature.

SIGHTING-091 stays OPEN as a known a11y gap; we don't fix it here. If a screen-reader-focused spec arises later, option A becomes the right move.

7. Why this didn't show up earlier

Spec-068? Spec-042's e2e gate? Outcome
spec-042's H2 component (run_table.py) used st.dataframe from day one. Synthetic + AppTest smoke tests passed. The test that would have caught it (Scenario B) was filed under spec-062 as a planned scenario, never implemented at the Playwright level until spec-063/064/065 needed it.
spec-063/064/065 added Scenarios C/D/E/F that all reuse Scenario B's "click 6437d335 row" preamble. All 5 inherited the same blocker. Re-running the suite for the first time (this session) surfaced it.
The v2_K duplicate-key crash earlier in this session masked Scenario A's failure mode too. Once the duplicate-key bug was fixed (commit 8346597), every scenario hit the gridcell timeout in seconds. Two distinct bugs, both surfaced by the same e2e run.
