2 Import design committed

Two ingestion paths behind one adapter interface. Picker is the everyday UX; Takeout is the GPS-preserving path. Both end by handing a local folder to the existing discover_images.

Path 1 · Picker API

OAuth → create session → open picker in browser → user selects → poll → download bytes (=d) to cache. Convenient, in-app. GPS stripped by Google.

Path 2 · Takeout folder

User points app at an unzipped Takeout export. We read media + supplemental-metadata.json sidecars. Full GPS preserved. Manual, bulk.

3 GPS recovery — what's possible verified vs. 2025/26 docs

Google's API intentionally strips location EXIF on download (both Picker and Library API: the =d param keeps all EXIF except location). Excluding CV landmark recognition, three non-CV routes exist — only one is exact and programmatic.

2Match to local originalExact Re-associate the Google copy with a local original by filename+timestamp (pHash fallback), lift GPS from its EXIF. Only works if the user still has originals — often false (Google is their archive). Opportunistic bonus.
3Maps Timeline correlationApprox Interpolate from the user's Location History track by capture timestamp (ExifTool-style geotag). Google moved Timeline on-device late 2024, killed web/Takeout export, kept ~90 days for many. Timezone/clock-sync footguns. Last resort only.
—API mediaMetadata.locationN/AField does not exist in current docs — never populated. Dead.
—Any param/scope that keeps GPSN/A=d is the only download form and it explicitly drops location. No scope changes byte content.
Three implementation gotchas (verified) — for whoever builds the resolver ① Sidecars were renamed to *.supplemental-metadata.json and Google clips filenames at ~46 chars, so naïve photo + ".json" matching fails — use prefix/fuzzy matching.  ② Treat 0.0, 0.0 as "no location," not Null Island.  ③ Prefer geoData (what the user sees, includes their manual edits) over geoDataExif (raw camera).
Accepted risk & the user-notification requirement Per product decision, we ship even though Picker imports arrive without GPS. The app must surface this: after a Picker import, show how many photos have no location and that geo/trip detection (spec-022) may be degraded, with a one-click "Recover GPS via Google Takeout" path. The GPS resolver runs a fallback chain — embedded EXIF → Takeout sidecar → local-original match → none — and records the source per photo so the UI can report coverage honestly.

4 Export design committed

A new sink, sibling to the existing album/export/folder.py & zip.py. Reads PipelineResult.selected_images (already the source of truth in sim_bench.db), uploads each file, then batchCreate (max 50/call) into an app-created album.

  • Scope photoslibrary.appendonly (+ edit.appcreateddata for album title/cover).
  • Google constraint: writes only to albums our app created — never the user's existing albums. UI must set this expectation.
  • Retry/backoff on 429; idempotent re-runs (skip already-uploaded via upload-token cache).
  • Both upload scopes are restricted → CASA audit only if/when distribution goes Public (§6).

7 The standalone smoke test your explicit ask

A single script, independent of Albumify (no FastAPI, no Streamlit, no sim_bench.db). It exercises the gphotos/ modules directly: opens a browser, does a real import, attaches GPS, and prints an honest coverage report.

File: scripts/gphotos_e2e_smoke.py  ·  live/manual (not in CI — needs a real Google account + browser)

# Picker import + GPS attach, end to end, outside Albumify $ .venv/Scripts/python scripts/gphotos_e2e_smoke.py --takeout "D:\Takeout" --out ".\_gphotos_smoke" [1/5] auth ......... opening browser for Google consent (loopback) OK [2/5] picker ....... browser opened — pick a few photos, then return 12 picked [3/5] download ..... =d bytes → .\_gphotos_smoke\cache\ 12 files [4/5] gps resolve .. exif→sidecar→local chain over 12 files IMG_8841.jpg 2025-08-14 10:22 47.4979, 19.0402 source=takeout IMG_8842.jpg 2025-08-14 10:31 47.4979, 19.0451 source=takeout IMG_8843.jpg 2025-08-14 11:02 -- -- source=none [5/5] report ....... GPS coverage 11/12 (92%) · exit 0

What it asserts

  • ≥1 item imported (else non-zero exit)
  • Each cached file is a readable image with a timestamp
  • GPS resolver returns a typed result per file with a source tag
  • Prints coverage % and the per-file source — proves we can attach GPS, and from where

Flags: --mode picker|takeout, --takeout DIR, --local DIR (original-match), --out DIR.

Why separate from Albumify

  • Isolates Google-integration failures from the app/DB
  • Runnable after P2/P3/P4 before any UI exists
  • No server to start; fast iteration on auth/picker/GPS
  • Doubles as the manual acceptance gate for P4

CI-safe siblings live in tests/gphotos/ with mocked HTTP + a fixture Takeout folder (the parser, resolver, cache, and session state machine all unit-test without network).
