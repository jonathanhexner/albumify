01 · What Modal is

Serverless GPUs, defined in Python

Modal is a cloud platform for running Python code on cloud machines — including GPUs — without managing servers, Dockerfiles, or Kubernetes. You describe the machine and its dependencies in Python, decorate a function, and Modal runs it on demand. "Serverless" here means: you never provision or keep a server running; Modal spins one up when a request arrives and tears it down when idle.

The old way

Rent a GPU server 24/7

Provision a VM with a GPU, install CUDA + drivers + deps, write a Dockerfile, keep it running (and paying) even at 3am with zero traffic, scale it by hand. Weeks of DevOps; a constant bill.

The Modal way

Decorate a function

@app.function(gpu="L4") on a Python function. Modal builds the container, finds a GPU, runs it per-request, bills per-second, and scales to zero when idle. The infra is the Python file.

For Albumify this matters because our pipeline needs heavy GPU models (InsightFace, DINOv2, RAM++, GeoCalib, CLIP) but traffic is bursty — a portfolio piece serves a handful of uploads, then sits idle for hours. Paying for a 24/7 GPU would be absurd; paying per-second only when someone uploads is exactly right.

02 · Core concepts

Five things, and nothing more

Modal's whole model is five primitives. Once these click, the code reads plainly.

App

A named deployment unit — a collection of functions + their resources. Ours: modal.App("albumify-curator").

Image

The container's contents, built from Python: a base OS + pip/apt installs + your code. e.g. Image.debian_slim().pip_install("torch", ...). Modal builds + caches it in the cloud. No Dockerfile.

Function

A normal Python function wrapped with @app.function(gpu="L4", image=..., volumes=...). That decorator is where you say "run this on a GPU, in this image, with these disks." Call it with .remote(args) and it executes in the cloud.

Volume

A persistent cloud disk that survives between runs — for data too big to bake into the image. We put the ~GBs of model weights + the HuggingFace cache here, uploaded once.

run vs deploy

modal run = execute once (dev/smoke). modal deploy = publish a persistent endpoint others can call by name (Function.from_name(...)) — what the live app uses.

The key mental shift

There is no separate infrastructure repo. The container image, the GPU choice, the disks, and the business logic all live in one Python file that you version alongside your code. "Infrastructure as code" taken literally — it's just Python.

03 · Scale-to-zero & cold starts

You pay only while code runs

This is the property that makes a GPU affordable for a bursty portfolio app. When no one is uploading, zero GPU instances exist and the bill is $0. A request wakes one up ("cold start"), it runs, then it's torn down after a short idle.

traffic
idle (hours) upload! idle
GPU state
0 instances cold start running scaled to 0
billing
$0 billed per-second $0

Cold start = the seconds to pull the cached image + mount volumes + load models into GPU memory. Mitigations we use: models on a Volume (not re-downloaded), a cached image, and keeping the model-load inside the warm function. Modal also offers memory snapshots to shrink this further.

The trade: the very first request after idle pays the cold-start latency. For a portfolio app that's acceptable (and the showcase trips render instantly from precomputed data while a live upload spins up — spec-106). A 24/7 service would instead keep one instance warm.

App("albumify-curator")
The deployment unit. Everything below belongs to it; the name is how the control-plane API finds the function later.
two Images
Smoke vs full, on purpose. The full image's dep set is finicky (numpy<2 for pyiqa, transformers for RAM++, onnxruntime-gpu, geocalib) and will need iteration on first deploy — so the trivial smoke_image lets us prove the GPU path in 30s before fighting the big image.
add_local_python_source
Ships our code into the container as importable packages — no pip install of the repo, no publishing. curate imports sim_bench.pipeline exactly as on your machine.
Volumes (/models, /cache)
The ~GBs of weights live here, not in the image. Baking them in would make every image build huge and slow; a Volume is uploaded once and mounted on every run. HF_HUB_CACHE points at the cache volume so RAM++ etc. download once.
device → "cuda"
The one pipeline change. Steps take a device config knob (default cpu); curate flips each to cuda. The engine code is otherwise identical to the local run.
gpu="L4", timeout=1800
The resource request. An L4 (cheap inference GPU) for up to 30 min/job. Change the string to "A10G"/"A100" if timing demands — a one-word edit.
06 · Deploy lifecycle

From code to a live GPU endpoint

Who does what. Red = only you can (your Modal account/billing); green = Modal does automatically.

1

Authenticate

you · once

modal setup → browser login. Writes a token so the CLI can talk to your account.

2

Prove the GPU (smoke)

you · 30s

modal run …/modal_app.py → Modal builds the light image, grabs an L4, runs gpu_smoke, prints cuda_available: True. Confirms account + GPU + path before any heavy work.

3

Build the full image

Modal · automatic, cached

First call to curate triggers Modal to build + cache the full image (pip/apt/our code). Slow once; instant after. Iterate here if a dep clashes.

4

Upload models

you · once

modal volume put albumify-models ./models /models. The weights land on the Volume; HF-downloaded models self-populate the cache volume on first run.

5

Deploy

you

modal deploy …/modal_app.py → curate becomes a persistent named endpoint. The control-plane API calls it via Function.from_name(...).

6

Serve

Modal · automatic

Each upload spins up a GPU, runs curate, returns the album, scales back to zero. You pay per-second of run time only.

The honest boundary

Steps 1, 2, 4, 5 are yours — they need your Modal auth and billing, which Claude cannot do. The code (steps 3/6 logic) is written and verified to construct; it gets runtime-verified when you deploy. Same pattern as the local VLM: real code, verified on real hardware by you.

Per 100-photo album

If GPU lands ~0.3–0.5 s/img → ~30–50 GPU-seconds → ~1–2¢ on L4. (Estimate — the real number is step 2–3's output.)

Guardrails

Input cap + rate limit (spec-106) + a Modal budget alarm bound worst-case spend even under a traffic spike.

Context: the CPU baseline was 9 s/img and non-interactive. GPU is both faster (lands the ≤3–5 min bar) and, at portfolio volume, cheaper than a single hour of a rented GPU for a whole month of demos.
