The core idea: Modal lets us write curate() as an ordinary Python function and add one line — @app.function(gpu="L4") — that means "run this on a cloud GPU, only when called, billed per second." No server to manage. When idle, there is literally no GPU running and the cost is $0.

Your question 1

The whole pipeline on GPU, or just some steps?

ANSWER
Whole pipeline on one GPU box — because the CPU-only steps are ~2% of the time

The pipeline mixes GPU steps (the models) and CPU-only steps (pure logic: triage rules, clustering, final selection). Measured on the real baseline, the CPU steps total under 0.2 s/image out of 9 s. So running them on the GPU box "wastes" GPU on ~2% of the work — not worth the complexity of a second machine.

RAM++ / GeoCalib / InsightFace / CLIP / DINOv2 / YOLO

triage logic · clustering · select_best
~2%
v1 — what we do

All 38 steps on the GPU box

One function call, one machine, simplest. Pay GPU rate for the tiny CPU slice — negligible. curate() runs execute_spec() with device=cuda.

later — if ever

Split CPU steps to a cheap CPU box

Saves ~2% GPU cost but adds cross-machine data shuttling + orchestration. Only worth it at large scale. Not now.

So: yes, the entire pipeline runs on the GPU instance — deliberately, because splitting would add real complexity to save almost nothing.

Your question 2

Pass the image bytes, or pull from shared storage?

ANSWER — you're right, this should change
Small test: pass bytes. Real albums: upload to storage, pass a reference, the worker pulls.

A Modal function call serializes its arguments, so it's only meant for small payloads (roughly a few MB). A 100-photo album is 100–200 MB — too big to stuff into a function argument. My current scaffold passes bytes inline, which is fine for a 40-image smoke test but wrong for production. Your instinct — pull from common storage — is the correct pattern.

scaffold only

Pass bytes in the call

curate(images=[(name, bytes), …]). Simple; OK for a tiny test. Breaks / is slow for a real album (args too big).

production

Upload → reference → pull

Browser uploads straight to storage (a Modal Volume or S3/R2). The API passes only a job id / path. curate(job_id) reads the photos from storage itself. The bytes never pass through a function argument.

Why storage is better beyond size: the upload (slow, user-paced) is decoupled from the compute (fast, GPU). The user can finish uploading before any GPU spins up, and the result also lands in storage for the viewer to read. This is a real correction I'll make to curate before it's wired to the live app.

Your question 3

Can an orchestrator warm the GPU up ahead of time?

ANSWER — yes, exactly
Fire a warm-up the moment upload starts, so the cold start overlaps with upload time

Cold start = the seconds Modal needs to grab a GPU + load the models before the first real work. Instead of paying that after the photos arrive, trigger a tiny warm-up call when the user starts uploading — the GPU boots while they're still choosing/uploading, and is hot by the time the bytes land.

Top: cold start happens after upload → user waits for it. Bottom: warm-up fires at upload-start, cold start hides under the upload → the saved time is real.

How, concretely, in Modal: when the upload page loads, the API makes an early call — either gpu_warm.spawn() (a no-op function that just boots a container) or Modal's min_containers / keep-warm for the duration of an active session. The expensive model-load happens during that window. This is the "orchestrator adds a cold-start stage up front" idea — it's a standard, supported pattern.

The trade to know

Keeping a GPU warm costs money (you're paying while it idles). So we warm up reactively (on upload-start), not permanently — preserving the $0-idle property while still hiding the cold start. A permanently-warm instance is only worth it for steady traffic, which a portfolio app doesn't have.

So, to pin it down

The three answers, together

1 · Steps: the whole pipeline runs on one GPU box (CPU steps are ~2%, not worth splitting).   2 · Data: small tests pass bytes, but production uploads to storage and passes a job reference — the worker pulls (a correction I'll make).   3 · Warm-up: yes — fire a warm-up when upload begins so the cold start hides under the upload; stay reactive to keep $0 idle.

What this means for the build order

First prove the path exists (modal setup → gpu_smoke, 30 s). Then the two real refinements your questions surfaced — storage-reference input and the warm-up trigger — become part of wiring curate to the spec-106 control-plane API. They're not built yet; your questions just defined them precisely.
