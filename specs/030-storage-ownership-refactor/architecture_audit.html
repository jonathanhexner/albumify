TL;DR — wrong diagnosis last round, here's the right one

The previous proposal ("prefer JSON when present") was a code smell, not a fix — it just shifts which redundant copy wins. The real problem is upstream: every piece of data is written to 2–4 places, no piece of data has a single declared owner, and readers pick a copy via existence checks (if foo.exists() chains).

This run produces 13 artifacts on disk, of which 9 carry the same information as something else. The merge-log bug is one symptom; clusters.csv getting renamed to clusters_stage_base.csv mid-export is another; faces_merged.csv existing at all is a third.

The fix is to declare ownership per data type — tabular relational data → DB; bulk numeric → npy; binary blobs → files; tiny human-facing summary → one JSON — and delete the duplicates.

6 information types · 21 storage locations. Every red box is a place where the data has to be re-derived during writes and re-resolved during reads. That's not a "DB schema bug" — it's a missing ownership model.

Smell · graceful degradation as architecture. Each branch silently swaps in a different data source. Why the visible bug appeared (now in this framing)

any one of the three and the bug disappears. Removing duplication is the only one that prevents the next bug of the same shape.

Storage principles — what should live where

Relational, queryable, joined

Faces, clusters, cluster_assignments, merge_decisions, run_metadata, face_scores.

→ SQLite. Schema must be the full fidelity of the in-memory dict (not a curated subset). Random access, joins, history queries.

Bulk numeric arrays

Embeddings (n × 512 float32). Distance matrices when cached.

→ .npy. Memmap-friendly, zero-copy load, native to numpy. Storing as DB BLOB is wasteful and not queryable anyway.

Binary blobs

Face crop JPEGs.

→ files in crops/. Streamable, browser-renderable, OS-cached. The DB's job is to hold the path, not the bytes.

Tiny, human-facing run pointer

"Which run is this? When did it finish? Where's the DB?"

→ pipeline_run.json. One small, stable JSON readable without sqlite3. Holds only: run_id, source_album, started_at, finished_at, status. Everything else in DB.

Anti-principle

If two artifacts can hold the same fact, one of them is wrong. Don't add an artifact "for convenience" — convenience is a query method, not a file. Convenience belongs in code, not in disk layout.

Target architecture

Invariants this enforces:
  • Every datum has exactly one owner on disk. Drift becomes structurally impossible.
  • Every reader goes through RunStore. Renaming a file is one-line refactor, not a grep.
  • If a run is half-written, RunStore raises — no silent fallback to a stale CSV.
  • Both apps produce byte-identical run layouts. The 2x2 matrix from before collapses to one cell.

Future storage model — exactly what each kept artifact contains

Five artifacts on disk per run. Nothing else. Every fact in exactly one place.

1 · face_clustering.db — the only relational store

2 · embeddings.npy + embedding_face_ids.npy — the only bulk numeric store

Shape and dtype

embeddings.npy
  shape: (n_faces, 512)
  dtype: float32
  L2-normalized

embedding_face_ids.npy
  shape: (n_faces,)
  dtype: int32
  row i of embeddings ↔ face_id at index i

Why two files instead of one

Numpy doesn't support heterogeneous columns. The id array is tiny (~1KB for 1000 faces), and keeping it explicit avoids the bug class where face_id ≠ row_index.

Loaded together by RunStore.embeddings() → returns a single object with both, never one without the other.

3 · crops/ — the only binary blob store

Naming convention (immutable)

crops/face_0000_aligned.jpg
crops/face_0001_aligned.jpg
crops/face_NNNN_aligned.jpg

· 112 × 112 px
· JPEG quality 85
· filename pattern is the contract

Why no manifest

crop_path in DB.faces holds the canonical path. The manifest JSON was a workaround for not trusting the DB; it goes away.

If the DB says crop_path = crops/face_0042_aligned.jpg, that's the truth. If the file is missing, that's a real error and we surface it — no fallback to "guess from face_id".

4 · pipeline_run.json — the only human-readable run pointer

Full schema (small, stable)

{
  "run_id":       "20260508_000446",
  "source_album": "album",
  "producer":     "albumify",
  "parent_run_id": null,
  "started_at":   "2026-05-08T00:04:46",
  "finished_at":  "2026-05-08T00:05:31",
  "status":       "complete",
  "db_path":      "face_clustering.db",
  "schema_version": 4
}

Why JSON for this and only this

Humans need to glance at a run dir and know what's there without sqlite3. CI/scripts can grep "status": "complete". The DB has the same data in run_metadata — this file is a redundant pointer, not redundant data.

Hard rule: nothing in this file is read by any code that has access to the DB. It exists for human triage and shell scripts only.

Provenance — who creates each artifact, from what inputs

Read this from any column to any other column: "where does cluster_assignments come from?" → RunExporter._write_clusters → in-memory ClusterResult.clusters. "How does the FC App show face crops?" → RunStore.crop_path(face_id) → DB.faces.crop_path → file under crops/. Single arrow at every step.

Directory layout — addressing the sub-folder question

Today (partly conventional, partly chaotic)

results/
  album/                              ← clean: only fc runs inside
    face_clustering_20260508_000446/
    face_clustering_20260508_011042/
  Budapest2025/                       ← album
  Budapest_1_recluster_111551/        ← orphan! sibling of album
  Austria24_4_recluster_005203/       ← orphan!
  knn_clustering_results.json         ← orphan!
  extraction_full.log                 ← orphan!

Within an album: face_clustering runs are already in their own per-run folders — no contention.

At results/ top level: reclusters and stray files leak out as siblings of albums. This is the actual layout mess.

Proposed (tighten the convention everywhere)

results/
  album/
    face_clustering/
      20260508_000446/         ← producer:albumify
      20260508_011042/         ← producer:fc_app
      remerge_20260508_011500/ ← producer:remerge
      manual_20260508_011600/  ← producer:manual_merge
  Budapest2025/
    face_clustering/
      ...
  _logs/
    extraction_full.log        ← stray files quarantined

Invariants: every face-clustering artifact lives under <album>/face_clustering/<run_id>/. Reclusters belong to their parent album, not to results/ root. Producer is a field in run_metadata, not encoded in the directory name.

Honest caveat on the sub-folder idea: this layout is hygiene, not a fix. A sub-folder cannot prevent two writers from producing different schemas inside that sub-folder — only a single RunExporter can. Treat layout cleanup and the storage-ownership refactor as two independent specs; don't conflate them.

Learnings

L1 · Duplication is the disease, schema mismatch is the symptom

"Make the lossy schema match" only buys time until the next field is added. Eliminate the second copy and the class of bug goes away.

L2 · Existence-check fallbacks are unrecoverable design debt

if foo.exists() hides architectural confusion as graceful behavior. Each branch is a different program that nobody designed deliberately. Static-check them out.

L3 · One owner per fact

Pick the store that fits the data shape (relational → DB; matrix → npy; blob → file; pointer → small JSON). Anything else is convenience-driven duplication.

L4 · One writer, one reader interface

Multiple producers and ad-hoc readers turn the disk into an ABI nobody owns. A single RunExporter + RunStore pair makes layout changes refactors instead of archaeology.
