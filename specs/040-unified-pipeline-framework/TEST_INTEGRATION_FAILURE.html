What the test exercises

Runs the Albumify scene-selection pipeline end-to-end on the 10-image samples/ukbench/ fixture:

discover_images -> score_iqa -> filter_quality -> extract_scene_embedding
                 -> cluster_scenes -> select_best   (include_noise=True)

Stated purpose (from docstring): "At least one image should be selected from each cluster."

The failure

AssertionError: assert 5 == 3
  len(context.selected_images) == num_clusters
  where num_clusters = len(context.scene_clusters)

The actual end state (reproduced)

KeyValue
context.scene_clusters keys[0, 1, -1]
cluster sizes{0: 4, 1: 4, -1: 2}  (HDBSCAN found 2 real clusters of 4 imgs each + 2 noise)
len(scene_clusters)3  ← counts the -1 noise bucket as a "cluster"
selected_images[00001, 00003, 00004, 00007, 00008]  (5 images)

Cast

ClusterScenesStep

sim_bench/pipeline/steps/cluster_scenes.py:71-79
Writes context.scene_clusters: dict[int, list[str]]. The dict's keys include label -1 for HDBSCAN noise alongside real cluster ids: 
num_clusters = len([k for k in clusters if k >= 0])  # internal log
context.scene_clusters = clusters                       # but stored WITH -1
So len(context.scene_clusters) = real-clusters + (1 if any noise).

SelectBestStep

sim_bench/pipeline/steps/select_best.py:176, 234-256
Default max_images_per_cluster = 2. With include_noise=True, the -1 bucket is processed like any other cluster, contributing up to 2 picks. With the ukbench fixture the runtime split is: 
cluster 0 (4 imgs) -> picks 2
cluster 1 (4 imgs) -> picks 2
cluster -1 (2 imgs, noise) -> picks 1
total selected = 5

Why the assertion is wrong (two independent bugs in one line)

Bug 1 — counts noise as a cluster

test_integration.py:127
num_clusters = len(context.scene_clusters) includes the -1 noise key. Should be len([k for k in context.scene_clusters if k != -1]), matching the producer's own definition (cluster_scenes.py:97).

Bug 2 — assumes 1-per-cluster, but step picks up to max_images_per_cluster

test_integration.py:128 vs select_best.py:176
assert len(selected_images) == num_clusters would only hold if every cluster contributed exactly one selection. SelectBestStep's default is 2, so with any cluster of size ≥ 2 it picks 2 — the equality is impossible to maintain.

The docstring ("At least one image should be selected from each cluster") describes a different, weaker invariant than the assertion. The assertion was written as if equality held; it doesn't.

Verdict

Stale test, not a regression. Git log shows the test hasn't been touched since commit 3c30737 (unrelated cluster-debug-view work, well before spec-040). It has been failing as long as SelectBestStep's max_images_per_cluster default has been > 1 and HDBSCAN has produced any noise. Nothing in the current branch caused it.

Three ways to fix — pick one

OptionChangeWhat it really asserts
A · Match the docstring Iterate scene_clusters, exclude -1, and assert each real cluster contributes at least one image to selected_images. "every real cluster is represented" — the invariant the docstring promises.
B · Force one-per-cluster and keep the equality Pass "select_best": {"max_images_per_cluster": 1, "include_noise": False}, change RHS to len([k for k in scene_clusters if k != -1]). "with these tightened configs, picks == real clusters" — narrow but unambiguous.
C · Delete The neighbouring test_pipeline_produces_expected_outputs already asserts scene_clusters and selected_images are non-empty; this test adds little once the assertion is rewritten. Nothing; coverage drops slightly.

Recommendation: A — preserves the original intent at minimal cost; the failure mode it would catch (a cluster being dropped by select_best) is a real risk worth covering.
