1. Problem

Albumify's engine is real, benchmarked, and green in CI, but it ships as a research monorepo, not a product. The landing page already promises the live product — "Bring a trip. Leave with an album." We need to actually deliver it: a stranger uploads their own trip and gets a curated, face-tagged, story-ordered album back, from the real 28-step pipeline running live — without ever OOM-ing, hanging, or showing a stack trace.

The old draft dodged this by shipping precomputed trips (Direction A). That's a case study, not the "0→100, launched a service" signal the portfolio needs. This rewrite commits to the live service.

2. Goal / non-goals

Goal: A deployed, product-grade web app at a public URL where anyone can upload a bounded trip and receive a live-curated album (picks + why + people), plus the three precomputed trips as instant showcase seed and an honest "how it works / vs a frontier VLM" narrative.

Non-goals (v1): no accounts / login / persistence beyond a TTL'd anonymous session; no billing; no GPU requirement (CPU ships v1); no change to the existing Streamlit apps; not a rewrite of the engine.

3. What makes this buildable now

spec-104 process isolation (merged to main). Each pipeline step runs in a spawned child that exits and returns 100% of its model memory to the OS, with a per-step wall-clock timeout. Measured capacity (spec-104 report): peak RSS is model-floor bound (~2.5 GB + ~0.67 MB/img), runtime-bound at ~1.6 s/img CPU, ~4 GB/worker. That turns "a live pipeline is reckless" into "a live pipeline is bounded."

6. Bounded-input contract (proposed defaults — see plan.html §6)

Max 150 photos / 25 MB per file / 1.5 GB total; JPEG·HEIC·PNG (decode-probed); per-step timeout 600 s; rate limit per IP/hour; upload TTL 1 h, result TTL 24 h. Server-enforced before any compute.
