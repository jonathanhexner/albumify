The Live Curator

Rewrites spec-106 from the precomputed showcase (Direction A) to the shippable product (Direction B): a stranger drops in their trip and gets a curated, face-tagged, story-ordered album back — from the real pipeline, running live.

"Bring a trip. Leave with an album." — the landing page already makes the promise. This plan is how we keep it without the run ever OOM-ing, hanging, or embarrassing us in front of a recruiter.

01 · What changes

From a case study to a service

The old spec.md shipped precomputed trips as static JSON — bulletproof, but a demo. Direction B runs the real 28-step default_pipeline on a visitor's own upload. Same engine; a completely different risk surface. The precomputed trips don't disappear — they become the instant-load showcase seed that fills the gallery before anyone uploads.

The one thing that makes B buildable

The pipeline used to OOM above ~120 images (SIGHTING-117: stacked model memory torch won't free in-process). spec-104 process isolation (merged to main) runs each step in a spawned child that exits and returns 100% of its model memory to the OS — plus a per-step wall-clock timeout that kills a hung step instead of hanging the request. That's the difference between "a live pipeline is reckless" and "a live pipeline is bounded."

03 · System architecture

Static edge, durable queue, disposable workers

The UI is static on Vercel and never talks to a model. A thin FastAPI control plane accepts a bounded job and enqueues it. A separate, scale-to-zero worker pool pulls jobs and calls execute_spec(...) with isolate_steps=True. Uploads and results live in object storage; job state in a small durable store. Nothing about the request path holds a 2.5 GB model.

04 · Job lifecycle

Every state is designed, including the ugly ones

A job is a small state machine. The UI has an intentional screen for each terminal state — a rejected upload, a timeout, and a crash all look considered, never like a stack trace.

CREATED→ REJECTED bounds fail ↑ · valid ↓
CREATED→ QUEUED→ RUNNING→ SUCCEEDED · FAILED · TIMED_OUT · EXPIRED
RUNNING relays the four passes as steps complete 01 Score — IQA · AVA · occlusion · tilt→ 02 Dedupe — DINOv2 scene · time/GPS→ 03 People — InsightFace · kNN · merge→ 04 Order — coverage-first · straighten

REJECTED

Too many photos / too big / unreadable format. Says exactly what to change. No compute spent.

TIMED_OUT

isolate_step_timeout_s tripped on a stuck step. Offer retry with fewer photos.

FAILED

A step crashed / child OOM. Parent survives (spec-104), job marked failed with the step name.

EXPIRED

TTL elapsed; uploads + results purged. Viewer shows a graceful "this run has expired."

05 · Why it's safe now

The memory math, measured not assumed

The spec-104 capacity experiment (Germany, 768 px, CPU) measured peak process-tree RSS across album sizes. The result is what makes a live service sizable: peak is model-floor bound, not image-count bound.

2.5 GB
model floor — ~93% of peak RSS
0.67 MB
added peak per image (isolated)
~1.6 s
per image, CPU — the real ceiling
~4 GB
per worker → k = RAM/4 GB, capped by cores
Peak RSS for a 500-image run (isolated)
model floor ~2.5 GB per-image ~0.3 GB @500 headroom

Flat scaling: isolated ≈ 2,511 MB + 0.67 MB/img; in-process ≈ 2,341 MB + 0.38 MB/img. No N² term (the only N×N producer, build_scene_distance, is gated off). 16 GB ≈ 20k images by memory — but runtime bites first.

What isolation buys the service

Survives OOM

A step that blows memory kills only its child; the worker returns a failed job instead of dying silently.

Survives a hang

Per-step wall-clock timeout (default 600 s) → SIGTERM→SIGKILL. A stuck download or deadlock can't wedge a worker forever.

Bounded RSS

Costs +~300 MB peak / +10% time vs in-process — cheap insurance for a public endpoint.

Known caveat — SIGHTING-122

Isolated vs in-process runs diverge by ±1–2 faces at N=300/500 (borderline detections flipping — suspected detector nondeterminism). Irrelevant to a curated album a human looks at, but it means we must not advertise bit-exact determinism, and the spec-104 §5 equivalence test carries a tolerance. Root-cause is tracked, not blocking.

07 · Data contract

One normalized shape the UI reads

The worker's execute_spec output (context.selected_images, people_clusters, scene_clusters, metrics) + the RunExporter dir get normalized into a single album.json the viewer consumes — identical in shape to the showcase seed, so live results and precomputed trips render through the same components.

// the normalized result the viewer reads — same for live jobs and showcase seed
type Album = {
  jobId: string; source: "live" | "showcase"; createdAt: string;
  counts: { uploaded: number; kept: number; people: number; scenes: number };
  picks: Pick[];            // ordered keepers (the album)
  people: Person[];         // face clusters → distinct people
  vlm?: VlmView;            // showcase trips only; required "N=1 pilot" caveat
};
type Pick = {
  id: string; thumb: string; full: string; order: number;
  score: { composite: number; sharpness: number; aesthetic: number;
           occlusion: number; tilt: number; faceCoverage: number };
  beat: string[];            // dropped near-dupes from its scene cluster
  people: string[];          // person ids present
};
type Person = { id: string; faceCount: number; sampleCrops: string[] };

New selection knob required. Today there is no global "K=20" — select_best picks per-cluster (max_images_per_cluster: 2, min_score_threshold: 0.4). A live album wants a predictable total, so Phase 1 adds a global top-K cap over the per-cluster picks. This is a real (small) engine change, specced separately if it grows.

08 · Hosting

Where the heavy worker lives

Vercel hosts only the static/edge front end — it can't run torch. The worker needs a model-capable host with scale-to-zero (portfolio traffic is bursty and mostly idle; we should pay ~nothing at rest). The engine is CPU-viable at 1.6 s/img, so GPU is an optimization, not a requirement for v1.

Recommendation

Vercel (front end) + Modal (worker + queue + storage). It collapses the "durable queue," "worker packaging," and "scale-to-zero" boxes into one Python-native platform, keeps idle cost near zero, and reads as a modern serverless-ML deploy. Fly.io is the fallback if we want plain containers.

09 · Cost model

Idle-cheap, per-run predictable

At rest

Vercel static: free/near-free. Worker scaled to zero: ~$0. Storage: pennies for a few expiring runs.

Per run (150 imgs, CPU)

~4 min × ~4 GB CPU worker ≈ single-digit cents on Modal-class pricing. Bounded by the input cap.

Blowup guardrails

Rate limit + input cap + job TTL bound worst-case monthly spend even under a traffic spike. Set a hard budget alarm.

Portfolio reality: this will serve tens of runs, not thousands. The design goal is "costs ~nothing when nobody's looking, never surprises me with a bill" — met by scale-to-zero + hard input/rate bounds.

10 · Roadmap

Seven phases, each with a hard gate

Back-to-front: prove the engine runs headless in a container before building any UI. Every phase ends green and standalone, so we can stop at any gate without a half-baked artifact.

P0

Contract & harness

De-risk before infra. Pin the bounded-run contract and the normalized album.json.

  • Add the global top-K selection cap over select_best picks (+ test).
  • Define Album/Pick/Person types; write the normalizer from context + RunExporter dir.
  • Headless script: folder → execute_spec(isolate_steps=True) → album.json on the 3 real trips.
Gate: one command turns a folder into a valid album.json matching showcase shape.
P1

Containerized worker + queue

The engine runs as a scale-to-zero worker pulling durable jobs.

  • Package the pipeline + models into the worker image (Modal).
  • Durable queue + job store; worker calls execute_spec, emits step events, owns persistence.
  • Adversarial memory test: max-N upload under isolate_steps → bounded peak RSS, no OOM.
Gate: enqueue a 150-img job by hand → album artifacts land in storage; peak RSS bounded; a killed step fails the job cleanly.
P2

Control-plane API

Public, bounded HTTP surface replacing _jobs + BackgroundTasks.

  • POST /jobs (bounds guard → presign → enqueue) · GET status · GET result.
  • Progress relay (SSE/poll) from worker step events.
  • Rate limit, TTL/expiry, rejection responses (413/415/429).
Gate: curl an upload end-to-end; every bound returns a clean typed rejection, not a 500.
P3

Next.js front end

The funnel: land → drop → watch → album → people.

  • Port design tokens from albumify_landing.html; both themes.
  • Dropzone with client-side bounds; live progress (four passes); album + people + why-picked viewers.
  • Every job state has a designed screen (queued/rejected/timeout/failed/expired).
Gate: a real upload from a browser produces a rendered album; all states designed.
P4

Showcase seed

Gallery is alive before anyone uploads — the old Direction-A asset, reused.

  • Ingest the 3 precomputed trips into the same album.json shape as static seed.
  • "How it works" (four-pass explainer) + honest vs-VLM panel (required N=1 caveat).
Gate: first paint shows curated trips instantly; live + showcase share one component set.
P5

Harden & load-test

Make the first-run-never-embarrasses promise true.

  • Cold-start budget; concurrency test (queue backlog UX); adversarial uploads (HEIC, huge, zero faces).
  • Cost/budget alarm; privacy pass (TTL purge verified).
  • Responsive + perf pass; no horizontal scroll; album interactive fast.
Gate: AC1–AC10 hold on the public URL, from a device that isn't Jonathan's.
P6

Review & ship

Close the mandatory gate.

  • /code-review → REVIEW.md; resolve High findings.
  • CHANGES_LOG + README (run + deploy in one command each); flip spec to Implemented.
Gate: public URL linkable from a resume; REVIEW.md clean.
11 · Acceptance criteria

The anti-half-baked gate, for a live service

Phase-1 "shipped" means every one of these holds on the deployed URL, cold, on a machine that is not Jonathan's.

AC1
Loads & works first try. Public URL, cold; showcase trips render with no console errors.
AC2
A real upload succeeds end-to-end. A stranger's ≤150-photo trip returns a curated album, people, and why-picked — from the live pipeline.
AC3
Every job state is designed. Queued, rejected, timeout, failed, expired all have intentional UI — never a blank or a stack trace.
AC4
Bounds are enforced server-side. Over-count / oversized / unreadable / rate-limited uploads return clean typed rejections; no 500s, no runaway compute.
AC5
Never OOMs. An adversarial max-N upload completes or fails cleanly with bounded peak RSS (isolate_steps proven under load).
AC6
Progress is truthful. The four passes reflect real worker step events, not a fake timer.
AC7
Data honesty. Shown numbers match the run; vs-VLM carries its "preliminary pilot, N=1" caveat; no determinism over-claim (SIGHTING-122).
AC8
Privacy. Uploads + results expire on TTL and are purged; the anon session holds nothing forever.
AC9
Responsive + themed + fast. Phone-width, both themes, no sideways scroll; album interactive quickly.
AC10
Idle-cheap & capped. Worker scales to zero; a budget alarm + rate/input caps bound worst-case spend.

13 · Open decisions

Calls needed before P0 starts

These change the build; the rest I can proceed on with the proposed defaults.

1 · Host

Modal (recommended) vs Fly.io vs something you already pay for. Drives the queue/storage wiring in P1.

2 · Input cap

150 photos is the proposed ceiling (~4 min CPU). Higher = better demo, worse cost/latency. Your number.

3 · Content-safety stance

Public anon upload of strangers' photos. Minimum ToS + short TTL, or add a safety pre-check? Blocks public launch, not build.

4 · GPU now or later?

CPU ships v1 fine (1.6 s/img). GPU cuts latency but adds cost/complexity — defer to a P5 optimization unless you want the speed for the demo.

5 · Accounts?

v1 assumes anonymous + expiring. Confirm no login/persistence in scope for the first public build.

6 · Album size (K)

The new global top-K cap — fixed (e.g. 20) or scaled to trip size? Affects the P0 selection change.
