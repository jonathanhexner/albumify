The critical path from where we are to a deployed, honest, resume-linkable portfolio piece — and the discipline to get there without another rabbit hole.

Two kinds of "done": it runs reliably, and the picks are good. The engineering is the known part. Quality is the bet — so we prove it first, cheaply, before building the expensive parts around it.

01 · Where we are

Status, honestly

The reliability foundation is built and the design is thought through. What has not been established is the one thing the whole portfolio rests on: that the curated picks are good enough to impress a stranger.

✓ Done / proven

  • spec-104 process isolation — merged to main; the live pipeline can't OOM/hang. The enabler.
  • Capacity measured — ~2.5 GB floor + 0.67 MB/img; ~1.6 s/img CPU; ~4 GB/worker.
  • Model-to-task evidence — tagging method fix; RAM++ wins content tagging; occlusion/blur stay on dedicated tools (defect experiment).

◐ Designed / in flight

  • spec-106 live curator — full plan drafted (plan.html); not built.
  • Agentic & semantic layer — design note; spec-105 (VLM merge arbiter) drafted.
  • spec-102 quality A/B — harness built, Budapest pilot prepped; no verdict yet.

✗ Unproven / undecided

  • Curation quality on fresh photos — the central unknown. Benchmarks measure retrieval, not "right picks".
  • The service — nothing deployed; no queue/worker/UI built.
  • Host & content-safety stance — undecided; block serving.
02 · Two gates

Reliability is mostly solved; quality is the real gate

Gate 1 — does it run?

Reliability · ~80% there

spec-104 killed the OOM; bounded input + per-step timeout + a durable queue (spec-106) close the rest. This is engineering with a known path — risky to execute, not risky to believe.

Gate 2 — are the picks good?

Quality · unproven

No human has blind-rated the picks (spec-102 has no verdict). If a recruiter's upload returns mediocre picks, the polish is wasted. This is cheap to test and must be settled before the 4–6 week serving build.

The discipline this plan enforces

Stop exploring, start converging. The last several sessions (tagging models, RAM++, defect detection) were valuable but are engine enrichment, not the path to shipping. From here, every piece of work must answer: "does this move us toward a deployed, quality-proven app?" If not, it's v1.5.

03 · The critical path

Prove → finalize → build → polish → ship

Sequenced to de-risk the cheap-but-decisive thing (quality) before the expensive thing (serving). Each stage ends at a gate; two gates are genuine go/no-go.

STAGE A

Prove the picks — quality validation

Settle, on evidence, whether the curation is good enough — before building anything around it. The harness already exists; this is days, not weeks.

  • Run spec-102 blind A/B (even solo N=1, honestly labeled) on the 3 trips.
  • Benchmark on PhotoTriage (best-of-burst) + CUFED (album importance vs human votes; report Kendall tau).
  • Eyeball picks on 1–2 un-tuned rolls (fresh Google Photos export).

GO/NO-GO GATE 1: are the picks good enough to put in front of a stranger? Pass → Stage B. Fail → targeted engine fix (now we know which pass is weak: scoring / dedup / ordering), re-test, then B. Do not start serving until this passes.
STAGE B

Finalize the engine

Lock the production curation path and the config knobs the live product needs. Minimal, driven by Stage A's findings.

  • Add album_max_picks (global top-K) — today selection is per-cluster with no total cap.
  • Fix whatever Stage A flagged (and only that); lock the production profile.
  • Confirm the normalized album.json contract (shared by live + showcase).
  • Scope the agentic/semantic layer — decide what (if anything) is v1 (see §04).

STAGE C

Build the live service — spec-106

The product: bounded upload → real pipeline on a scale-to-zero worker → curated album. The 4–6 week core.

  • P2 control-plane API (bounds guard, job endpoints, progress relay).
  • P3 Next.js front end (upload → live progress → album → people), every state designed.
  • P4 showcase seed (the 3 precomputed trips, instant first paint).

Parallel & lightweight — the narrative

Runs alongside C/D, low effort: the "how it works" 4-pass explainer, the honest vs-VLM panel (N=1 caveat), and a short technical write-up linking the benchmarks. This is what turns "an app" into "a story a hiring manager remembers."

04 · In scope vs deferred

v1 ships reliable + honest; v1.5 adds agentic depth

The agentic layer is a strong hiring signal and genuine quality — but it is not on the critical path to a shippable v1. Ship the reliable curator first; add agentic depth as a fast-follow (or pull exactly one piece forward if it's cheap and visible).

TierWhatWhy here
MUST (v1)Reliable live curation on bounded upload · quality proven acceptable · deployed URL, every state designed · honest framing (N=1, no determinism overclaim)This is the portfolio piece. Without these it isn't shippable.
SHOULD (v1)People view · why-picked score breakdown · showcase seed trips · "how it works" explainerCheap, high-impact depth; mostly reuses existing data.
COULD (v1.5)Agentic layer: VLM merge arbiter (spec-105) · album-type tuner · story + keeper captions · RAM++ content tags + thematic grouping · adaptive K / min-per-personThe "agentic AI" résumé signal + quality lift. Fast-follow once v1 is live and quality-proven.
WON'T (v1)Accounts · billing · GPU · live model training · multi-user persistenceOut of scope; not needed to prove "I launched a real ML service."

Optional pull-forward: if Stage A shows merge/dedup is the weak link, the VLM merge arbiter becomes quality-critical and may move into v1. And keeper captions (Tier-2, ~20 images, cheap) are the one agentic piece that adds visible polish for little cost — a reasonable single pull-forward.

06 · Risks to finishing

What actually threatens the finish line

Scope creephighest
The real risk: every subsystem has an interesting rabbit hole (we just did three on tagging). Mitigation: freeze v1 scope (§04); gate new work behind "does it serve shipping?"; park ideas in the v1.5 list.
Quality shortfallhigh
Picks turn out mediocre on fresh photos. Mitigation: Stage A first and cheap; if it fails, a targeted fix to the weak pass — not a rebuild — then re-test.
First-run trustmed
A slow/failed first upload kills credibility. Mitigation: instant showcase seed + honest queue/progress + cold-start budget (Stage D).
Cost blowupmed
Public endpoint + heavy models. Mitigation: scale-to-zero + input/rate caps + TTL + budget alarm.
Solo bandwidthmed
One person, 4–6 week core. Mitigation: strict critical-path order; defer all v1.5; narrative runs in parallel at low cost.
07 · Definition of done

What "finalized" means

The project is a finished portfolio piece when all of these hold — not before, and nothing more required.

Public URL loads cold, works first try on a device that isn't yours.
A stranger's bounded upload returns a good curated album, live.
Curation quality validated (a number + honest framing), not hoped.
Every job state designed — queued/rejected/timeout/failed/expired.
Never OOMs under adversarial input; spend is capped.
AC1–AC10 (plan.html) all hold on the deployed URL.
"How it works" + honest vs-VLM narrative live (N=1 caveat).
REVIEW.md clean · CHANGES_LOG · README (run + deploy one command).
URL linkable from a resume — the one-line pitch is true.
v1.5 ideas parked in a backlog, not half-built in v1.
The immediate next action

Stage A — run the quality validation. It's cheap (harness exists), it's the highest-information thing we can do, and its result determines everything downstream: either "quality's good, go build the service" or "here's the weak pass, fix it first." Everything else waits behind it.
