01 · The four planes

Who does what — and the trust boundary

Four layers, each with one job. The split that matters most: the browser is untrusted (it never holds a long-lived secret); the GPU plane is expensive (used only for model compute); storage decouples the slow upload from the fast compute.

Golden rule: the browser talks to storage only through short-lived, narrowly-scoped presigned URLs the control plane mints — it never receives storage keys or the Modal token. Everything expensive or secret lives behind the control plane.

02 · Job lifecycle

Warm-up and upload run in parallel

The moment the user commits, two things fire together: the browser begins uploading the 768px images, and the control plane triggers the GPU warm-up. The cold start hides under the upload; by the time the last byte lands, the GPU is hot.

browser
downscale + upload 768px (small) watch progress view album
control plane
fire warm-up + presign curate(job_id) serve result
Modal GPU
cold start + load models warm, waiting pull → pipeline → write result scale to 0

Warm-up (orange) overlaps the upload (blue) — it isn't added on top. The GPU is hot when curate (green) starts. Models load once at container start (Modal @enter) and stay resident for the real call.

Sequence: (1) user commits → (2) API presigns + fires warm-up → (3) browser uploads 768px straight to storage → (4) API calls curate(job_id) → (5) worker pulls from storage, runs pipeline, writes album.json + keeper displays back → (6) browser reads the result via signed URLs → (7) GPU scales to zero. Net user wait ≈ max(upload, warm-up) + curate compute.

03 · Resolution tiers

Upload small, keep full-res for what you download

The models work at ≤768px and the pipeline was validated there, so analysis never needs full-res. Downscaling in the browser makes the upload ~15–20× smaller and keeps originals on the device.

768px · ALL
Analysis + review. Every photo, downscaled in-browser, uploaded. Powers the pipeline AND the "see everything / why dropped / override" view. ~0.2 MB each.
~1600px · keepers
On-screen album. Display versions of the selected set (and any the user promotes). Lazily produced after selection; plenty for viewing.
original · on demand
Download only. Full quality, one photo at a time, only for what the user actually keeps. Stays on the device unless downloaded/shared.

Floor: never below 768px (sharpness/occlusion/blur are calibrated there). Ceiling: full-res gives analysis nothing (models downsample internally) — so we never upload it for analysis. The 768px tier does double duty: curation input and the browse-everything review surface.

04 · Show-everything principle

Curation is a proposal, not a verdict

A curator that hides the 80 it didn't pick is presumptuous and breaks trust. Every input photo stays visible, carries the reason it was dropped, and is one click to promote into the album. Same rule as triage's set_aside (spec-107) — never silently hide, always recoverable — now applied to selection itself.

# the result groups EVERY photo by why, not just the winners
★ Album (the picks)        ordered keepers + why each won
  Near-duplicates dropped   "beaten by this pick in its moment"   # the "what it beat" data
  Low-quality dropped       "blurry / occluded / tilted"
  Set aside (junk)          "screenshot / document"                # spec-107 set_aside
      every item → shows the reason + a "keep anyway" button

Cost: zero extra upload — the browse-everything view runs off the 768px copies already uploaded for analysis + the result metadata. This is both better product (the user can argue with it) and a better portfolio story ("it explains itself").

05 · Secrets & keys

What's secret, where it lives, who never sees it

Three secrets exist. The one rule that governs all of them: secrets live on trusted hosts (as platform-managed env vars / secret stores), never in git, never in the container image, never in the browser. The browser only ever gets short-lived, narrowly-scoped tokens.

How the browser uploads without ever holding a key

# 1. browser asks the control plane for an upload target (no keys involved)
POST /jobs  → control plane (holds S3 creds) mints a presigned PUT URL:
     scoped to ONE prefix (jobs/<id>/), write-only, expires in ~10 min
# 2. browser PUTs the 768px images straight to storage with that URL
     the raw S3 keys never leave the control plane; the URL can do nothing else
# 3. worker reads those objects using creds injected by a Modal Secret
@app.function(secrets=[modal.Secret.from_name("albumify-storage")])
def curate(job_id): ...   # boto3 reads S3 env vars Modal injected at runtime

Platform secret stores

Prod secrets live in Vercel env vars (control plane) and Modal Secrets (worker) — encrypted at rest, injected as env vars at runtime. Not in code.

Local dev

.env (gitignored) for the API; modal setup stores the Modal token in ~/.modal.toml. The repo's .gitignore already blocks .env.

Least privilege + expiry

A presigned URL writes to ONE job prefix and expires in minutes. If leaked it can't touch other jobs or read keys. Rotate the long-lived creds periodically.

The three nevers

Never commit a secret to git (use env vars + a gitignored .env). Never bake a secret into the Modal image (use modal.Secret, injected at runtime). Never ship a long-lived key to the browser (mint a scoped, expiring presigned URL instead). The browser is untrusted by design.

06 · Data contract

One album.json the UI reads

The worker writes a single normalized result. It carries every photo (not just picks) with its selection reason — the data the show-everything view needs — plus the picks, people, theme, and captions.

type Album = {
  jobId: string; createdAt: string;
  counts: { uploaded, kept, people, scenes, setAside };
  picks: Pick[];            // ordered winners + score breakdown + "what it beat"
  dropped: Dropped[];       // EVERY non-pick + reason {near-dup|low-quality|set-aside}
  people: Person[];         // face clusters → distinct people
  theme: AlbumTheme;        // album_type, motifs, caption (spec-108)
};
type Pick    = { id, order, thumb768, display1600, score:{sharp,aesthetic,occlusion,tilt,faces}, beat:string[], people:string[] };
type Dropped = { id, thumb768, reason, reasonDetail, promotable:true };   // one click → picks

Shape is identical to the precomputed showcase trips, so live results and seed trips render through the same components. promotable:true encodes the show-everything principle in the contract itself.

08 · Build order

Prove each seam before stacking the next

1 · Prove the GPU seam

modal setup → gpu_smoke → first real curate on a storage reference. Establishes the data plane works + the per-image GPU latency.

2 · Storage + presign

Object store + the mint-presigned-URL endpoint. Prove a browser can upload 768px directly and the worker can pull it.

3 · Control-plane API

POST /jobs (bounds + presign + warm-up + enqueue), GET status, GET result. Secrets via env/Modal Secret.

4 · Front end

Upload + in-browser downscale → live progress → album + show-everything viewer. Every job state designed.

5 · Showcase seed

Precomputed trips in the same album.json shape → instant first paint.

6 · Harden & ship

Adversarial uploads, cold-start budget, TTL/privacy, cost alarm, /code-review, deploy.

Each step ends green and standalone; the GPU seam (1) is first because everything else assumes it works. Full phase detail: plan.html.
