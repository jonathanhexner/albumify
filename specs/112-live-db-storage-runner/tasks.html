spec-112 — Tasks (Live DB + storage, runner as config)

Status: In Progress — Phase A A1–A5 built 2026-10-10 (63 new tests); A6 real-data proof folded into Phase A2's proof (W5). Phase A2 (album workbench) approved 2026-10-23 (O3 = 7 days, O4 = pipeline name only); W1 in progress. Spec: spec.md · updates · roadmap stage C · ROADMAP.md

Design notes

  • Rows in the DB, bytes in storage, compute cache local. Storage map: spec §2.
  • Job layout unchanged. jobs/<id>/{input/, album.json, display/, run.json} from spec-110 plus a new results/ (run.db, embeddings.npy, face crops). JobCurator keeps working on a local directory; JobSync moves files in and out of the object store.
  • ObjectStore interface (sim_bench/serving/object_store.py): put_file, get_file, list(prefix), exists, delete_prefix, download_url(key, ttl). Phase A: LocalObjectStore. Phase B: R2ObjectStore (boto3).
  • Worker writes storage only. DB writes happen in JobService / the loader (API process or CLI).
  • Control DB = separate engine (sim_bench/control/), never sim_bench.db, never the per-run run_db factory (they must not be cross-imported, see sim_bench/run_db/_session.py).
  • Loader reuses the run schema read-side: open results/run.db with the run_db models, map to control-DB rows keyed by (job_id, photo_id) / (job_id, face_id).
  • Runner protocol: run(job_id) -> RunOutcome. LocalRunner runs JobCurator in a child process (spec-104: torch memory is only freed by process exit). ModalRunner: Phase A shells out to the existing driver path; Phase B calls the deployed function via modal.Function.from_name.
  • New deps: Phase A none expected; Phase B boto3, psycopg[binary], moto (fake S3, tests).
